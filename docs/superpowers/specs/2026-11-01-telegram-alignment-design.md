# Telegram 机器人与主脚本对齐设计

用户于本会话确认优先实施：共用维护锁、统一健康检查来源、机器人副本版本检查与更新。本文件落实已经确认的方案；不提交、推送、连接 Telegram 或部署真实主机。

## 方案与范围

采用“共享主脚本检查接口与维护约束，TG 保留交互和确认”的方案。继续各自维护检查逻辑会逐渐分叉；将主脚本全部交互菜单搬入 TG 会扩大远程修改范围，均不采用。

主脚本新增 `--status-json`：调用与终端相同的只读采集函数，输出版本化 JSON（检查项、必检项、结论、范围、采样时间），不输出原始诊断或凭据。机器人读取该接口，20 秒总预算、30 秒缓存，失败明确显示检查未完成，不把轻量检查冒充完整检查。旧配置保留轻量检查兼容并标明范围。修改成功使缓存失效。

机器人确认后的修改操作共用 `/run/lock/crowdsec-1key.lock`，非阻塞获取；迁移未完成时拒绝修改。获取失败、目录/文件不安全、迁移状态不明确均不执行。保留身份校验、一次性确认和持久化操作记录，锁失败为明确未执行。

安装时随附独立主脚本运行副本（入口及 lib），采用既有托管 runtime 的 release/current 发布机制；机器人无需源码目录或 cron。配置记录固定 runtime 入口和维护路径。配置/程序/辅助模块/current 链接纳入回滚；未知归属、链接 helper、无效配置拒绝更新。旧菜单 1–3 保留，新增 4 版本检查、5 保留配置更新。只读比较主程序、helper 与 runtime 指纹；配置与状态不纳入代码指纹。源码更新、cron 副本同步、机器人更新三者明确区分。更新预览影响，默认取消；保留配置字节及原 enabled/active 状态，不自动启用原停用服务。

## 验证与边界

先添加并运行失败测试，再实现。隔离测试覆盖共享 flock 争用、迁移拦截、失败不执行、锁释放；JSON 与终端同一采集来源、异常/超时不降级为健康、不同配置/节点范围；自包含安装、代码差异、取消、配置保留、服务状态保持、启动失败回滚及未知路径拒绝。最后运行机器人组合与全仓回归、语法、ShellCheck、文档链接和 diff 检查。

真实拦截始终需要按入口、协议、地址族、新连接与时间验证。服务运行、命令成功和历史验收不替代真实业务验收。本会话没有独立 reviewer 工具，最终进行单独顺序自查并披露。
