# 第二台 VPS 防护整改设计

用户已确认专项复审建议并授权执行。操作证据及业务配置留在权限为 0700 的私有目录；公开文档以“站点 A”代称商店。

## 筛选请求成本

站点 A 的 `/shop`、`/shop/` GET/HEAD 商品筛选请求，在现有每 IP 限速之外共享最多 2 个并发请求、每秒 1 个请求及 burst=2 的预算；超限返回 429。预算与 User-Agent、来源 IP 数量和 Cookie 无关。原有明确爬虫拒绝逻辑保留。在首次 server rewrite 阶段对标准化路径及含百分号编码的参数前缀分类，使用缓存的 map 结果保持内部转发时的分类；验证编码路径、重复斜线和点路径均进入同一预算。

这些限制只覆盖含 `products-` 查询的商品筛选页。普通商店页、商品详情、购物车、结账、账户、API 和 POST 不使用新预算。暂不缓存带会话信息的动态响应。若需要更高吞吐，必须依据筛选耗时和实际购买转化调整，而非直接增加 PHP 并发。

## 检测及执行

验证去除筛选场景中依赖爬虫自报 User-Agent 的条件后，浏览器标识的快速枚举能够触发，正常低频筛选不触发；保留原阈值。分布式低频请求由前述总预算保护。

追踪有效决策与两个 nftables 集合的并集；用隔离来源验证添加、续期、到期和删除，避免封禁 SSH 管理来源、CDN 节点或其他真实访客。无法复现的历史缺口必须明确记录，不宣称已修复。

续封测试已复现有效长封禁在旧内核期限到达时失效，IPv4/IPv6、TCP/UDP 均受影响；官方源代码的全集合去重会跳过已有地址而不刷新 TTL。最新官方版本的同一 nftables 逻辑没有变化。因此整改选用现有官方程序支持的 iptables/ipset 后端，先在完全独立的网络命名空间验证续封、删除及自然到期，再切换生产配置。保留 INPUT 和 FORWARD，并接入 DOCKER-USER。切换时用临时的原有封禁快照保护流量，验证完成后移除；不引入定时补洞脚本或自编译 Bouncer。

补齐已确认的 AppSec 拒绝回退 HTTP 403 修复，同步对应托管资源摘要。初次整改保留故障策略；用户随后明确反对 AppSec 故障放行，追加更正为 `APPSEC_FAILURE_ACTION=deny`，同步配置资源摘要，并验证拒绝连接、超时及 HTTP 503 均返回 403、业务后端零命中，健康对照返回 200。LAPI 故障策略不在此次追加调整范围。仅移除重复的独立 cron 更新任务，保留发行包 timer。

## 发布与验收

先使用本机实际 OpenResty 在环回地址运行独立实例及可计数的测试后端，证明旧配置缺少总预算，新配置限制分散来源、普通浏览器、内部转发后的昂贵请求，业务对照请求可达后端。AppSec 故障注入验证旧版 200、新版 403 和后端零命中。

每项变更先保存原始字节、元数据、前后 SHA256 和拒绝覆盖后续编辑的回滚脚本；写入前检查并发修改。配置检查通过后才优雅重载，并观察主进程不变及新 worker。上线后核对页面、配置摘要、服务状态、实际封禁与恢复。无真实订单或支付授权时，支付仅验证读取页面及隔离请求路由，不创建订单。
