# Telegram 健康查询响应与展示设计

用户已确认本轮健康展示、查询响应、缓存提示及 VPS 更新范围。继续使用现有功能分支和混合工作树，不提交、不推送；保留历史验收和线上状态。

健康简版和详情均展示同源 summary.verdict。实际拦截项目用中性名称“实际拦截验证”，pending 显示待验证，不能暗示已通过。页尾明确采样时间及本次采样／复用 30 秒缓存。

仅 overview、status 两个含完整健康采集的页面放到单个后台线程；其他导航和修改继续由主循环顺序处理。后台最多保留 8 个卡片请求，同卡片只保留最新请求，不建无界线程／队列。命令先发送可返回的查询中卡片，再编辑结果。回调先答复，采集期间仍可导航和取消。导航或操作使同卡片旧任务失效，过时结果不能覆盖新页面；发送的临界区仅含发送请求，采集不占锁。繁忙明确提示重试。

正常进入、简版／详情切换可复用缓存；健康页面独立 fresh: 回调表示强制采样，重复刷新可复用请求后已经完成的采样。成功修改继续清除缓存，并使正在进行的健康结果失效，避免旧采样冒充修改后的状态。完整接口失败仍显示检查未完成。

Telegram API 客户端已有状态锁；主循环在处理前保存 offset 的语义保持。异步任务为只读，重启可能丢失查询结果；不重放修改。现场更新通过产品的保留配置更新入口，校验配置字节、offset、审计和服务意图。真实 TG 专门验收只做已授权且可直接验证的安全部分；不能冒充用户点击 Telegram 按钮。
