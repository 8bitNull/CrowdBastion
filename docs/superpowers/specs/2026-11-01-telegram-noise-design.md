# Telegram 通知降频设计

用户已于本轮批准：需要关注首条及时提醒、后续每小时合并；普通每六小时汇总，并检查发送中新增事件与重试。实施和 VPS 更新沿用当前工作树，不提交或推送。

每个节点共用一个关注窗口。节点首次关注通知可立即发送；其成功后 3600 秒内的新规则和同类新增事件都等待下一次合并，不因攻击来源或规则变化绕过窗口。普通汇总为 21600 秒，无新增不发。时间从成功回执计算；Telegram 429 和消息失败退避继续持久化，紧急、恢复和人工测试不受两类汇总窗口限制。发送期间产生的新计数必须留待下次发送，不能误记已投递。

VPS 仅修改现有配置的 `policy.attention_interval_seconds=3600` 和 `policy.digest_seconds=21600`，保留其他策略和规则等级；通用默认及其他已部署节点不批量迁移。修复调度器中发送期间快照变更留下的过期待发汇总，以及快照变更导致失败退避未落到当前队列的问题。投递选择阶段再次检查窗口，成功后清理同一汇总槽；新增事件留在 incidents/events 中，窗口到期重新构造。

仅修改本轮通知程序和两个配置项。远端新管理发布目录以已部署版本为基础叠加本轮文件，避免发布工作区其他混合改动；同步日常入口、root 管理副本和 bot 随附管理副本中的通知源文件，bot 自身程序不变。通知服务单独重启，CrowdSec/Bouncer/Docker/交互 bot 无须重启，路由和防火墙不变。

一致性 SQLite 备份只供审计；失败回滚恢复代码、配置和管理指针，保留活队列、消费进度、offset 与审计。INT/TERM/异常尝试恢复，不承诺 SIGKILL/断电事务恢复。真实生产通知正常运行，不另外发送测试消息；聊天收件次数和六小时实等不作为本轮已通过项。
