# 中心 CrowdSec 与中转 Bouncer 运维边界

中转节点只运行 Firewall Bouncer 时，中心 LAPI 提供决策，中转防火墙执行决策。Bouncer 不读取 SSH 日志，也不自动识别 gost/realm 转发流量中的攻击。原 `--install-relay` 仍包含本地 CrowdSec，不能把这两种模式混为一谈。

## 中心准备

在中心部署 CrowdSec，为每个中转创建不同的 Bouncer 账号（例如 `cscli bouncers add relay-a`），仅把对应密钥交给该中转。中心应通过可信私网或 WireGuard 地址提供 LAPI，限制访问来源；跨公网使用经过证书校验的 HTTPS。不要直接开放裸 HTTP LAPI 到公网。账号密钥应存入密码管理器，避免进入终端历史、工单或截图。

先验证中转能访问中心，再配置中转的远端 Bouncer。已有 CrowdSec 节点改用远端决策后，其本地决策不会自动发送给远端中心；本工具不会自动迁移、停用或卸载已有本地核心。务必明确哪一个中心负责决策。

## SSH 日志集中采集

若需要保护中转 SSH，须另行将中转的认证日志送到中心。可使用已有 rsyslog/syslog-ng，经 WireGuard 或双向 TLS 传输，按节点写入独立文件；中心将这些文件作为 `type: syslog` 的 acquisition，并安装 linux/sshd 集合。发送端须保留原始 SSH 消息、时间和攻击来源 IP。不能将转发接收端的传输来源地址替换成 SSH 日志中的攻击来源地址。

本阶段不自动安装日志转发器。启用之前，检查中心对每个节点的文件有读取权限，发送重启不会重复收集过量旧日志，时间同步正常；使用受控失败登录验证中心解析到的是原始客户端 IP。中心发出的 ban 应由该中转 Bouncer 同步执行。仅查看 Bouncer 服务为 active，无法证明整个检测链已建立。

如所有中转共享同一个中心决策流，一个节点触发的 IP 决策可能在其他中转同步生效。日志发送方及共享决策节点应处于同一可信管理域。遭到篡改的日志可能诱导中心误封。

## 故障与维护

远端失联时，新决策无法同步。此次官方 Bouncer 0.0.36 / nftables 的短时实测显示：未到期封禁仍执行，短期封禁可在断连期间到期，恢复连接后可同步解除；正常停止会清理表，重启重建并同步存在防护间隙。详见[实际验收记录](audit/2026-10-12-remote-bouncer-validation.md)。其他版本和配置应重新验收。不要把“服务运行中”当作“远端连接健康”，也不要在失联时自动清空封禁或生成宽泛白名单。

上述 2026-10-12 记录未覆盖续封。2026-10-19 已确认 0.0.36／0.0.38 的 nftables 实现可能在原截止时间删除仍有效的续封条目，见[第二台 VPS 修复对照](audit/2026-10-19-second-vps-remediation.md)。当前新装默认 iptables/ipset；已有受影响节点需备份后安排迁移，并验证跨原截止时间仍阻断及正常到期／撤销恢复，详见[使用说明](usage-guide.md#防火墙后端与续封检查)。

更换密钥时，先在中心创建新账号，再修改对应中转配置并确认真实认证/业务验证，最后撤销旧账号。卸载本地托管 Bouncer 不会删除中心账号；中心管理员应单独撤销密钥。

## 实际业务限制

gost/realm 的应用层转发及 NAT/MASQUERADE 常使后端看到中转 IP。入口防火墙能针对入口来源执行 IP 决策，但后端日志未必保留原始客户端身份；两者不能互相代替。验证时应使用新的 TCP 会话及 UDP 探针，并保留正常客户端对照。已有连接和连接跟踪还可能影响观察。

该机制不能解决超过 VPS 带宽或上游容量的流量型 DDoS。此前 256 MiB Bouncer-only 短时模拟仅显示较小内存占用，不代表真实公网吞吐量、长期稳定性或完整 SSH 检测。
