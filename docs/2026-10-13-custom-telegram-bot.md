# 自定义 TG 机器人修复与接入

修复基于用户上传的 `crowdsec_bot.py`，原上传文件与 VPS 的 `/usr/local/bin/crowdsec_bot.py` 未覆盖。新版位于 `lib/crowdsec_bot.py`，保留九宫格、资源采样、告警查询、取证、NPM 日志抽样和原有操作入口。

## 原因与修复

原脚本执行 `cscli alerts inspect ID --no-metrics`。官方 CrowdSec 1.8.1 实测返回 `unknown flag: --no-metrics`，而原 `run_cmd` 忽略退出码和 stderr；取证正则继续解析空输出，导致“未知路径 / 未知 UA”。即使命令成功，人类可读输出也不是稳定的数据接口。

新版使用 `cscli -c CONFIG alerts inspect ID --details -o json`，支持官方返回的单个对象及数组；遍历事件 `key/value` Meta，识别 HTTP 与 AppSec 的路径、UA 和方法字段，解析告警上下文的 JSON 数组。样本来自同一事件，最多展示 3 组；只有 AppSec 单一上下文且路径一致时才补齐事件缺失值。多请求上下文不能证明路径与 UA 的对应关系时不强行组合。空 UA 与未记录 UA 分别显示，非 HTTP 告警说明不适用。

同时修复：

- 自动告警线程默认关闭，由官方 HTTP 通道唯一推送。查询和按钮产生的是用户请求响应，服务启动不主动发送上线消息。
- 告警卡片展示实际附带决策和模拟状态，不再写死“内核 DROP 4 小时”；告警时间不称为已验证拦截时间。
- 命令使用参数数组、检查退出码和超时；封禁/解封校验 IP 与时长，不再通过 shell 插入用户输入，不再把失败显示为成功。
- 手动封禁复用主菜单的本机／管理员地址保护，检查接口地址、管理员解析白名单和显式 own/admin 地址记录，拒绝 loopback、unspecified 及其 IPv4-mapped 表示。接口查询或安全记录无法读取、格式错误时拒绝提交决策；不向 Telegram 返回配置内容。
- 按钮与普通消息同时核对管理员个人 ID 和聊天 ID，支持群组负数 Chat ID。TG API 校验 JSON `ok`、拒绝重定向，长轮询 HTTP 超时大于等待时间，不打印含 Token 的异常。
- 同 Token 的本工具实例共享文件锁；轮询 offset 私有保存并按 Token 隔离，避免服务重启重放已领取更新，Token 更换不沿用旧 offset。更新在执行前记录，进程崩溃时可能丢失该次请求，应重新查询状态再重试。
- 白名单首次生成有效 YAML，原文件未知格式保留不改；修改前校验、失败恢复并报告恢复不完整。加白仅代表日志解析白名单，不保证 AppSec、CAPI 或其他防护放行。
- NPM 取证为最多 8 个 access 文件、每个尾部 512KB 的抽样；不是全量统计或容量承诺。资源菜单也不再声称没有 OOM 风险。

封禁决策分页卡片、站点体检卡片与生产实际拦截证据要求见 [查询卡片说明](2026-10-13-telegram-query-cards.md)。

## 九宫格与卡片导航（2026-10-20）

使用 `/start` 显示常驻九宫格：

| 📊 防护总览 | 🚨 最近告警 | 🚫 封禁决策 |
| --- | --- | --- |
| 🔍 告警取证 | 📈 攻击分析 | 📦 容器状态 |
| 🤖 机器人状态 | 🛠 运维工具 | ❓ 使用帮助 |

“防护总览”展示资源和防护健康；“机器人状态”展示轮询、投递与待核对操作。“攻击分析”归并告警统计、可疑来源与请求路径；后两项来自 NPM 日志有限抽样，不能单独作为恶意身份或实际拦截的证明。“容器状态”展示 Docker 健康与接入配置，仍不主动检查网站 HTTP 可用性。“运维工具”提供日志解析白名单查看，以及经确认后执行的重载、释放文件缓存。

查询卡片提供刷新、返回上级或主菜单。点击卡片的详情、翻页、刷新和返回会编辑原消息；返回主菜单时显示同样的九个内联入口。再次发送菜单文字或斜杠命令会发送新卡片。`/inspect ID` 和告警卡片的取证按钮固定调阅指定告警，刷新保留该 ID；九宫格“告警取证”及不带 ID 的 `/inspect` 查询最新告警。

推荐流程是“最近告警 → 告警取证 → 查看此 IP 当前决策 → 决策详情 → 操作确认”。最近告警和取证卡片不直接展示解封/加白按钮；决策详情对有效 IP 目标提供操作入口。历史告警不代表当前决策，未在本次查询范围中找到该 IP 时不展示修改按钮。手动 `/ban IP [时长]`、`/unban IP`、`/white IP` 继续可用，均需确认。

新增查询命令为 `/overview`、`/alerts`、`/decisions`、`/analysis`、`/containers`、`/bot`、`/tools`；原有 `/status`、`/inspect`、`/top`、`/help` 保留。旧九宫格文字仍映射到对应页面；旧消息上的分页、取证、白名单查看和修改按钮继续处理，修改操作仍进入确认流程。更新安装后执行 `/start`，可刷新客户端显示的常驻键盘。

## 操作确认与运行诊断（2026-10-20）

所有修改操作现在先展示影响，再由同一管理员在同一聊天内点击“确认执行”：手动封禁、解封、永久加白、引擎重载、释放文件缓存均适用。斜杠命令和旧消息上的按钮采用相同流程。确认有效期为 60 秒，只能使用一次；取消、超时或服务重启后需重新发起。查询直接响应。加白会修改日志解析白名单、重载 CrowdSec，并提交删除该 IP 全部决策的解封操作，确认页会说明适用范围。

执行前在私有状态目录写入持久化操作记录；记录无法保存时拒绝执行。记录包含操作 ID、UTC 时间、管理员与聊天 ID、动作、目标和结果，不包含 Token 或命令原始输出。结果先保存，再向 TG 回复；回复失败不会自动重复执行。进程中断或结果不能确认时，先查实际决策或服务状态再决定是否重新发起。审计文件为按 Token 隔离的 `bot-actions-*.jsonl`，单文件达到 1 MiB 时轮转，保留 3 份备份；独立 pending 文件保留待核对记录。

`/status` 展示防护健康、最近成功轮询、最近成功发送、当前 API 问题、下次轮询重试时间和最近待核对操作。“系统大屏”也加入健康摘要，标题使用本机主机名。检查本机 CrowdSec、LAPI、Firewall Bouncer、组件登记及日志读取/解析；单次检查总预算 20 秒，结果缓存 30 秒，并注明采样 UTC 时间。未配置的可选组件、空闲日志、读取失败分别显示；数据库不可读时决策数显示“未知”。TG 的检查范围限于这些组件，完整网站、代理链和规则检查仍使用主程序 `--status`；服务运行与决策存在不能证明实际拦截。

网络诊断区分 401 身份认证、403 权限、409 同 Token 轮询冲突、429 限流、服务端故障、超时与响应格式问题。轮询按指数退避重试，最高 60 秒；429 遵循 Telegram 返回的有效 `retry_after`，可能等待更长时间。消息发送采用单次尝试；超时或连接故障时，送达状态仍需核对。成功回复按钮回调不会清除之前的消息发送错误。

本机可直接读取运行记录，不连接 Telegram：

```bash
sudo python3 /usr/local/lib/crowdsec-1key-bot/crowdsec_bot.py --runtime-status
```

自定义配置增加 `--config /实际路径/config.json`。退出码 `0` 表示近期运行记录正常，`1` 表示记录了 API 错误或读取检查失败，`2` 表示尚无有效记录、轮询记录超过 90 秒或存在待核对操作。记录只反映最近一次采样，需同时核对 systemd 服务状态；交互机器人菜单“只读检查”会展示两者。更新时仍需通过“配置/更新并启用”复制新版程序及配套模块，单独重启旧服务不会升级文件。

## 在 VPS 使用

1. 更新完整项目，包含脚本和 `lib`。
2. 核对并停用旧自定义机器人的轮询服务/cron，保留原脚本备份。官方 HTTP 通知保留。不要同时运行旧机器人与新版轮询同一 Token。
3. 在项目目录执行：

   ```bash
   sudo bash crowdbastion.sh --custom-bot
   ```

   也可进入 `--telegram` 菜单第 5 项“可选交互机器人”。
4. 选择“配置/更新并启用”，填写 Token、Chat ID、管理员个人用户 ID、NPM 日志目录与 API 端点。Token 隐藏输入；留空沿用已保存值，首次可读取旧脚本中的静态参数。旧脚本参数只做 AST 字面量读取，不执行其代码。群组 Chat ID 与管理员个人 ID 不同，必须分别填写。
5. 在配置的聊天中发送 `/start`，然后用 `/inspect 告警ID` 核对路径/UA；核对按钮操作结果与实际 CrowdSec 决策。只读状态仅证明配置和服务状态，不证明 Telegram 轮询或生产拦截。

部署文件：

| 项目 | 路径 |
|---|---|
| 服务 | `crowdsec-1key-bot.service` |
| 程序 | `/usr/local/lib/crowdsec-1key-bot/crowdsec_bot.py` |
| 封禁安全检查（600） | `/usr/local/lib/crowdsec-1key-bot/crowdsec_safety.py` |
| 私有配置（600） | `/etc/crowdsec/crowdsec-1key-bot.json` |
| 状态目录（700） | `/var/lib/crowdsec-1key-bot` |
| 新机器人日志解析白名单 | `/etc/crowdsec/parsers/s02-enrich/crowdsec-1key-tg-whitelist.yaml` |

使用实际 `config.yaml` 的 DB 路径及 `-c` 参数，不假定 CrowdSec 数据库路径；原脚本 DB 路径仅作为缺省回退。旧白名单文件保留，管理员应核对现有规则是否仍需要。

安装依赖 Python 3 和 PyYAML；安全检查模块随机器人部署。更新前备份配置、脚本、安全模块和 unit；启动失败恢复文件及原服务启用/运行状态。识别其他 CrowdSec 机器人服务、已知脚本进程或 cron 候选时拒绝启动，要求人工核对，不删除未知服务。即使同名服务位于 vendor/transient 路径，也检查 systemd 实际加载来源，只有本工具标记的服务才允许接管。名称/脚本扫描不能排除其他实现的同 Token 消费者，Telegram 409 冲突仍需排查其他节点。

交互机器人“停用”保留配置与程序，官方通知继续运行。确认卸载核心时会停用并移除受管理的机器人 unit、程序和状态，备份及旧独立脚本保留。此组件默认以 root 运行，以支持现有决策、白名单和重载操作；Token 与配置需保持私有，管理员权限等同于这些操作的主机权限。
