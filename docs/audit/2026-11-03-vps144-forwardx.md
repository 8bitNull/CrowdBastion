## 实际验收

生产 INPUT 验收使用临时 namespace／veth 的文档地址和正常对照来源，通过真实 LAPI 创建唯一理由的短期决策，由真实 Bouncer 同步。覆盖三个实际 realm TCP 监听和同一 INPUT 链后的私有 UDP 回显：

- 封禁前双方正常；封禁后测试来源被阻断，正常对照不受影响，实际来源集合 DROP 计数增加。
- 35 秒决策续封为 60 秒，越过原期限后仍被阻断。
- 精确删除本轮理由的决策后恢复；再次创建 12 秒决策，自然到期后恢复。
- 最后确认测试决策、地址集合成员、临时 UDP 进程、namespace、veth 全部清理。

新测试地址不在迁移时的临时封禁快照内，因此上述结果不依赖快照保护表冒充新 Bouncer。迁移验证通过后，从同一管理员来源的新 SSH 连接提交；临时 guard 表及回退 timer 已清理。

还使用**实际已安装的 realm 2.9.4 二进制**，在只含 loopback 的独立网络命名空间中复现三个端口及后端映射，运行 IPv4／IPv6、TCP／UDP、多客户端和 64／512／1200 字节回显。调整前、调整后均完成 **36 个客户端用例、108 次逐字节一致的往返**，没有客户端响应串线；两次实验全部清理。实验只修改影子配置，不重启生产 realm，也不修改宿主机 sysctl／防火墙。

**边界：** 这证明了安装二进制的隔离转发完整性，以及生产 INPUT 的封禁生命周期。外部三个 TCP 入口已确认能建连，但未携带真实代理认证；实际公网 UDP 后端响应、协议认证、WAN 吞吐提升、已有长连接被封禁后的行为和冷启动没有验收。实验 IPv6 通过不代表公网 IPv6 可用，该 VPS 当前没有全局 IPv6 地址。

一键脚本更换 Bouncer 包时，dpkg 询问是否覆盖已修改的基础 YAML，非交互输入结束导致安装暂停。使用 `dpkg --force-confold --configure crowdsec-firewall-bouncer-iptables` 保留原文件后完成配置，再次运行一键安装成功。没有选择覆盖凭据，也没有删除／重建身份。

管理 Agent 在 **10:59:45 UTC** 出现一次正常 systemd 停止／启动，触发者未确认；本轮命令没有显式重启 Agent。它最终 active、NRestarts=0，但不能据此反推重启来源。三条实际 realm 始终保持原 PID 和原配置，不把管理 Agent 的变化隐去或当成转发进程重启。
