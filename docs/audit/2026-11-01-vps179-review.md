# VPS 179 调查后的三轮本地复审与修复

日期：2026-11-01。承接[现场只读检查与更新方案](2026-11-01-vps179-readonly.md)，本轮完成本地修复、部署副本回归与方案复核。没有执行远端部署、服务重启、规则修改、封禁验收或 Telegram 实际发送。

三轮均为本会话作者顺序自查，没有独立审查者。原有混合工作树保留，未提交或推送。本轮生产代码修改仅为 `lib/notify.sh` 的依赖清单；同时修改两份测试和通知使用说明。

## 第一轮：复现并修复通知依赖遗漏

根因是共享健康模块新增了 `crowdsec_bot_runtime.py → crowdbastion_ux.py` 的传递依赖，而通知安装清单仍只有 6 个程序文件。现有安装测试通过 `PYTHONPATH=tests:lib` 启动，安装目录缺失的模块会从仓库补到；原通知进程测试也直接运行仓库源码，所以没有覆盖这个部署缺口。

本轮修复：

- `NOTIFY_HELPERS` 增加 `crowdsec_bot_runtime.py`、`crowdbastion_ux.py`。同一清单驱动预检、备份、复制和清理，新增文件也随之进入这些流程。
- 新增安装回归：对实际安装目录运行配置检查，使用隔离 Python 并只显式加入安装目录，屏蔽仓库的导入路径。
- 原真实进程回归改为按安装清单复制独立程序目录，在隔离 Python 中从该目录运行；TLS API 使用本机模拟服务。

修复前两项检查均稳定失败于 `No module named 'crowdsec_bot_runtime'`；补齐清单后两项通过。进程检查继续覆盖真实 HTTPS 429、重启后限流保留、消息确认、组件故障与恢复；没有放宽原断言。

[RED](2026-11-01-vps179-review/round1-red.txt) → [GREEN](2026-11-01-vps179-review/round1-green.txt)。第一版隔离探针遗漏了显式加入程序所在目录，产生过 `crowdsec_bot_api` 无法导入的探针错误；修正探针后重新取得上述同因 RED。中间记录保留为 [harness-adjustment](2026-11-01-vps179-review/round1-harness-adjustment.txt)，不计为产品缺陷。

前轮的最小候选补丁已落实到源码。前轮报告及 manifest 保留原采样状态，其中“补丁未应用”描述的是当时状态；当前修复状态以本报告为准。

## 第二轮：失败和中断能否恢复完整副本

新增两项事务回归，实际注入复制失败和 TERM：

- 首次安装在最后一个新增依赖复制失败时，恢复官方通知原路由，删除本次新配置／unit／已复制程序，避免留下部分可启动副本。
- 已有服务更新时，先实际复制修改过的 runtime helper，再令后一个依赖复制失败或发 TERM。确认原程序、配置、profiles、unit 原文恢复，恢复通知服务；已入队的真实 SQLite 数据库文件与队列处理状态不被回退或清空。

通知策略、安装、真实进程及通知事务组合共 **59 项通过**，46.256 秒。此轮没有发现需要额外修改事务实现的问题。

证据：[通知与回滚组合验收](2026-11-01-vps179-review/round2-notification-green.txt)。这些测试通过临时目录和 systemd 命令替身验证文件事务及恢复意图，不代表真实 systemd 故障、断电或公网可达性的验收。

## 第三轮：新增私有路径与部署方案复核

对两个新增依赖分别放置未知普通文件、符号链接、FIFO，合计 6 个场景，均在备份／写入前拒绝，原通知路由和外部文件保持不变，不停止或重启已有服务。检查脚本只操作隔离 fixture，未调用主机防火墙。

[检查脚本](2026-11-01-vps179-review/guard-verification-script.txt)与[结果](2026-11-01-vps179-review/round3-ownership-green.txt)可复现这些路径检查。这是补充审计探针，不另计入全仓 unittest 数量。

复核部署方案后，明确以下条件：

1. root 的两条 `@reboot` 恢复任务与单个 `netfilter-persistent` 服务需要统一处理；两个 iptables unit 名只是别名。停用旧整表恢复前，先为要保留的静态规则确定启动归属。
2. 唯一静态 IPv4 规则是对 lo 的 TCP 81 DROP。它既不能作为公网管理端口限制，也可能影响 SSH 隧道。公网 81／3000 的访问策略需要依据实际可信来源确定，不应从当前监听状态推导出已限制访问。
3. 终端与交互机器人应更新为同源完整检查，但独立通知的默认监测范围仍为 CrowdSec、LAPI 和防火墙 Bouncer 进程。共享依赖完整不代表通知已覆盖网站业务或真实阻断。
4. 机器人保留配置更新与通知的“启用／更新”是两个操作。通知显式启用会执行 enable／restart；原计划中“服务意图保持”应理解为机器人及未选择变更的服务，以及失败恢复到原服务意图，不能承诺显式启用通知仍保持 disabled 或仅 runtime enabled。
5. 上轮约 9.36 秒是旧终端检查的耗时。新版完整 manager 必须在暂存目录实际测量，并通过机器人 reader 的 20 秒预算与结构验证，才能切换。
6. 更新源码不自动更新机器人、独立通知或 cron 运行副本；源码与 lib 必须完整发布。已在[通知说明](../telegram-noise-control.md)补充独立副本与保留队列的更新方式。

本轮没有修改远端配置，也没有重新采样 VPS。使用前轮的远端 SHA256 对修复后的本地候选重新比较，两个主代码目录均为 **33 相同、20 不同、9 缺失**；相较前轮多出的一个不同文件是本轮修复的 `lib/notify.sh`。不能把这份重算结果当作远端已经更新的证据。

证据：[候选代码比较](2026-11-01-vps179-review/candidate-comparison.json)。
