## 如何配合 CrowdSec

推荐沿用当前结构：

```text
客户端／上游 → 179 本机 INPUT 来源 IP 封禁 → realm → 后端服务
                         ↑
               本机 Firewall Bouncer
                         ↑
             本机 CrowdSec LAPI／IP 决策
```

1. **基础防护：保留当前核心和 Bouncer。** 宿主机 realm 是用户态监听，关键路径为 INPUT，不依赖内核 DNAT 的 FORWARD。来自社区情报以及本机 SSH、网站检测的 IP ban 会在流量进入 realm 前执行；规则同时适用于 TCP 和 UDP。无需为两个 realm 端口分别安装 Bouncer，也无需迁移现有 iptables 后端。
2. **业务行为检测：优先使用后端的可靠事件。** realm 负责转发，不理解加密流量中的认证是否成功。需要后端协议服务提供真实客户端 IP、认证失败等可解释事件，再选择兼容 parser/scenario；不支持的日志需要定制和离线验证。当前 HTTP AppSec 仅覆盖已接入它的 HTTP 请求，不能检查任意 realm 转发的 TLS/QUIC 内容。
3. **多跳联动：在实际看见客户端网络源 IP 的入口执行封禁。** 当前普通用户态转发会新建到后端的连接，后端网络层通常只看见 179 的地址；本轮未登录后端核实。如果后端通过 PROXY protocol 记录了真实客户端 IP，可将可靠检测决策通过受认证的中心 LAPI 分发给入口 Bouncer。远程 LAPI 应走受限可信通道，保持认证和 TLS 校验，不直接公开裸 HTTP API；也可采用安全日志集中方案。
4. **共享上游：避免连带封禁。** 如果客户端前面另有共享入口，179 的防火墙只能按这个上游网络来源匹配。PROXY 头只改善应用获取真实 IP，不会改变内核数据包源地址；即使后端产出了用户 IP 的 ban，179 也未必能命中。应把封禁执行放到最前端，或采用能够识别真实用户身份的应用层执行方式。可信中转的排除策略应限定在相应检测和业务路径，不能用全机放行替代设计。

当前来源 IP 的 ban 是**全机生效**：同一个 IP 被本机网站检测封禁后，也会影响它访问 realm 和 SSH。若未来希望网站检测与中转业务隔离，需要另行设计决策范围／执行规则，不能假设现有全局集合天然按业务区分。

## 对 realm-xwPF 的具体注意事项

已核对用户给出的仓库，源码参考提交 `ef90071cca0073a4dd41f62708a6c9e82a27873c`。它是 realm 管理脚本，本身不会自动补齐本项目的 realm 行为检测。

- 脚本生成 `/etc/realm/config.json`，使用 `realm.service`，并与现场共用二进制路径 `/usr/local/bin/realm`。直接安装／更新可能影响现有 ForwardX 管理的二进制，启动相同监听端口还会冲突。切换管理器应作为单独迁移处理，CrowdSec 接入并不要求迁移。
- `lib/rules.sh` 的 Proxy Protocol 全局开关会同时设置 `send_proxy=true` 和 `accept_proxy=true`。普通客户端不发送 PROXY 头时，开启接收会使连接失败。直接面向普通客户端的入口应保持接收关闭；需要向兼容后端传递地址时，仅为对应规则启用发送。
- 中间跳只有在确实接收上一跳 PROXY 头时才启用接收；后端也必须使用支持相同版本的监听器，并限制可信代理来源，防止来源伪造。不能仅因开启头部就认为客户端 IP 已可信恢复。
- TCP 的配置与验证结论不能直接套用 UDP／QUIC；需要核实当前 realm 版本、后端协议及具体传递方式，分别验收。
- 管理脚本可能重新生成配置，因此日志／代理设置应进入实际管理器的持久配置，避免只编辑生成文件后被覆盖。

## 可选增强与实施顺序

建议先维持现有 IP 情报、SSH 和网站防护，确认上游拓扑及后端协议，再决定是否增加真实业务日志检测。若只需要转发入口的基础 IP 黑名单，这台 VPS 已具备所需组件。

如果需要抵抗连接耗尽，可额外研究按入口、协议和来源设置新连接速率／并发限制；这属于防火墙资源控制，不是现有 CrowdSec 自动提供的能力。共享出口可能有大量正常连接，不能未经基线测量就套每 IP 低阈值。UDP 还需要考虑地址伪造，不能用几个异常数据包触发全机自动 ban。仅按 realm 连接量、EOF 或后端超时封禁均不推荐。

端口扫描检测也不能只靠安装 `crowdsecurity/iptables` collection：现场虽已安装，但当前采集未配置对应内核日志。若确有需求，应另行设计有限速的日志规则与采集，先观察和验证，避免日志风暴和重复封禁。

最后进行可控的外部验收：使用独立测试来源与正常对照来源，逐项验证封禁前可达、封禁后测试来源的新连接被阻断、正常来源仍可达、规则计数增加、解封后恢复。覆盖两条实际入口及其使用中的 TCP/UDP；有公网 IPv6 后再验证 IPv6。测试来源不能使用当前 SSH 管理来源或共享中转来源。本轮没有创建测试决策，不能把已有 DROP 总计数当作这两条 realm 路径的验收结果。

带宽被打满的 DDoS 需要服务商或上游清洗；本机 CrowdSec 和连接限速都无法收回已经占满的接入带宽。
