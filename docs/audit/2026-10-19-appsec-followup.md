## 重复更新造成实际中断窗口

主机时区为 America/Los_Angeles，当日为 PDT（UTC−7）。三个每日任务均执行规则更新后重载：

| 来源 | 当地时间 | UTC | 命令特征 |
| --- | --- | --- | --- |
| `/etc/cron.d/crowdsec-autoupdate` | 03:30 | 10:30 | hub update → upgrade → reload |
| root crontab | 04:00 | 11:00 | hub update → upgrade **--force** → reload |
| root crontab | 04:30 | 11:30 | hub update → upgrade → reload |

CRON journal 记录了三次实际执行。核心文件日志与 Nginx 错误日志形成以下时间关系：

| UTC | 核心重载开始 | AppSec 恢复监听 | 期间连接被拒绝 |
| --- | --- | --- | --- |
| 10:30 | 10:30:09 | 10:30:19 | 所查尾部未取得样本 |
| 11:00 | 11:00:10 | 11:00:20 | 11:00:12，1 条 |
| 11:30 | 11:30:08 | 11:30:14 | 11:30:12，1 条 |

这些是三条每日任务，不是每半小时持续运行的单一任务。重载不改变主 PID 或 NRestarts，因此仅检查 active/running、PID 和重启计数会遗漏此类中断。

系统另有启用的 `crowdsec-hubupdate.timer`：每日运行，随机延迟最多五分钟。已读取其实际调用脚本，确认会检查 `hub upgrade` 输出，仅在有升级输出时执行 reload。今天当地 00:02:09–00:02:15 的执行结果为 success、退出状态 0。

建议的首个线上改动是：备份 root crontab 与上述 cron.d 文件，停用这三条重复的每日任务，保留系统 timer 及其脚本，保留其他 crontab 条目。该改动本身不需要立即重载 CrowdSec。验收应确认只剩一个自动更新来源、原有非 CrowdSec 任务保留、timer 仍启用，并观察下一次执行结果。发生实际规则升级时，保留的任务仍可能重载；本建议减少冗余窗口，不声称实现无中断升级。

## 后续顺序与验收

1. 合并重复更新调度，消除已确认的不必要重载窗口。
2. 在隔离环境验证 AppSec 并发与通知队列，分别测量连接、等待检测结果的延迟及失败数量；验证增加 runner 或调整超时是否有效、是否增加内存占用。不要仅凭相关性直接修改线上数值。
3. 单独复现并修正 AppSec 失败拒绝分支的 HTTP 200 回退问题，验证拒绝时不回源。LAPI 失败处理需要独立验证；切换 AppSec 失败策略不能直接改变它。
4. 用独立测试来源完成网站／CDN 的“正常→封禁→撤销”对照，并测试检测引擎故障时的实际行为。此前 INPUT 测试不能替代此项。

第 1 项是范围明确、可回滚的调度清理；后续改变失败策略会影响故障期间的业务可访问性，应在隔离验证及策略选择后发布。
