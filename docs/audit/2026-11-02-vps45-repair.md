## 检查器修复

旧检查器要求每个入口第一条规则直接跳转 CrowdSec，误判现场合法的 `FORWARD → DOCKER-USER → CROWDSEC_CHAIN`。现在从各入口首条规则出发，仅追踪已声明用户链的无条件普通 `-j`，直到配置的 CrowdSec 链。条件规则、ACCEPT、RETURN、goto、缺失中间链和循环均拒绝；CrowdSec 链内来源集合 DROP 的严格检查保持原样。

产品变更仅为 [crowdsec_firewall_runtime.py](../../lib/crowdsec_firewall_runtime.py)；回归见 [test_firewall_runtime.py](../../tests/test_firewall_runtime.py)。没有调整正在工作的 Docker/CrowdSec 跳转顺序。部署前候选版本已在现场识别路径和 16,687 条适用网络入核、遗漏 0，同时仍报告两条真实开机 cron 风险，见 [staged-health.json](2026-11-02-vps45-repair/staged-health.json)。

## 静态开机策略与 cron

重新采集的 root crontab 仅含两条有效 restore 和一条已归并维护任务的注释。本轮按内容匹配并使用已有事务工具，分别备份后注释：

```text
# CrowdBastion disabled: @reboot iptables-restore < /etc/iptables/rules.v4
# CrowdBastion disabled: @reboot ip6tables-restore < /etc/iptables/rules.v6
```

第三行原注释保留。`/etc/cron.d/crowdsec-autoupdate` 字节及摘要保持不变，仍为 Asia/Shanghai 每日 03:30 执行 `--update-hub`。两份旧保存表只保留备份，没有执行 restore、flush 或整表回灌；netfilter-persistent 原本未安装，nftables.service 原本停用，本轮没有改变它们。

新建 `/usr/local/lib/crowdbastion-vps45-static/apply.py` 及 `crowdbastion-vps45-static.service`。服务位于 local-fs 之后，Docker、Bouncer 和 1panel-agent 之前，active/enabled。双栈独立 `CB45_STATIC` 链保留以下既有语义：

| 流量 | 处理 |
| --- | --- |
| 回环、RELATED/ESTABLISHED | ACCEPT |
| TCP 53322（SSH）、29726（1Panel）、80、443 | ACCEPT |
| UDP 443 | ACCEPT |
| 其余 TCP/UDP | DROP |

本服务先检查既有链内容和每条精确规则，再按需创建/追加；只在 INPUT 追加自己的跳转，不替换其他规则。失败仅逆序删除本次新增项，已有不一致链拒绝修改。SIGINT/TERM 尝试清理；不承诺断电或 SIGKILL 下的事务恢复。将来调整管理/网站端口时应同步审阅此静态服务及 1Panel 策略。

部署时断言除该链及其 INPUT 跳转外，原双栈 `iptables -S` 完整内容不变。远端隔离网络命名空间中真实 iptables/ip6tables 各创建 9 条规则，重复运行完全不变；现场仅重启新静态服务后规则仍逐字一致，四个原有服务 PID/状态/重启计数和启动时间不变。证据：[isolated-static.json](2026-11-02-vps45-repair/isolated-static.json)、[static-restart.json](2026-11-02-vps45-repair/static-restart.json)。这证明该脚本的创建、幂等性及现场重执行，不代表整机冷启动验收。
