# 2026-10-19 第二台 VPS 防护整改及验收

已确认并修复一个可以重复触发的封禁续期缺口，同时为高成本商品筛选请求增加总预算。本次经用户确认后执行；目标地址、业务域名及管理员来源仅保留在私有证据中。详见[脱敏验收证据](2026-10-19-second-vps-remediation-evidence.json)。

原 nftables 后端收到一个地址的新决策时，若该地址已经存在于任一托管集合，就直接跳过，不刷新内核超时。本机实测：先封禁 35 秒，再追加 95 秒封禁，旧期限到达后两个地址的决策均仍剩约 65 秒，但 IPv4、IPv6 集合条目都消失，TCP、UDP 测试流量随即恢复通行。这证明存在实际漏拦；此前历史地址的具体缺失事件仍不能逐条还原。

该分支见官方 [v0.0.36 nftables 源码](https://github.com/crowdsecurity/cs-firewall-bouncer/blob/v0.0.36/pkg/nftables/nftables.go#L170)。核对官方 v0.0.38 后，同一后端的这两个源码文件没有变化，因此本次没有替换 Bouncer 二进制。

已改用现有官方程序的 **iptables/ipset 后端**，iptables 本身仍使用 nf_tables 兼容模式。补装 ipset，保留 INPUT、FORWARD，并接入 DOCKER-USER；IPv4、IPv6 的六个入口都检查了 CrowdSec 跳转顺序。切换期间使用原封禁集合的临时快照保护流量，随后移除；原有 1Panel 规则经对比保持一致。Firewall Bouncer 为切换后端重启一次，CrowdSec 未重启。

| 验收项目 | 结果 |
| --- | --- |
| 生产环境 IPv4／IPv6、TCP／UDP 续封 | 旧期限到达后继续拦截；删除决策后恢复；对照来源始终可通 |
| 独立命名空间、实际内核和现有 Bouncer | 续封、跨来源决策删除、自然到期均通过 |
| 有效封禁与内核集合 | 最终快照中剩余至少 15 秒的 17,787 条有效决策无缺项；排除临近到期的采样竞态，同一地址的多条决策允许对应一个集合成员 |
| 网站原 WAF 与 Web Bouncer | 200 → 403 且后端零命中 → 200，对照来源持续 200 |
| Cloudflare 真实 IP | 独立请求的出口、回源访客地址和 CF 头一致，TCP 对端属于受信任 CDN 网段 |

商品筛选现在共享 **最多 2 个并发、每秒 1 个请求、burst=2** 的预算，超限返回 429，同时保留每 IP 限速及原爬虫拒绝逻辑。分类使用首次 rewrite 阶段的标准化路径，并识别百分号编码的参数前缀；缓存分类结果，使 WordPress 内部转发后仍保持限制。

真实 OpenResty 的隔离后端测试中，旧配置允许 8 个来源同时进入后端；最终配置只允许 2 个，其余 6 个返回 429。补查还发现，仅匹配原始 URI 会被编码路径、编码参数、重复斜线及点路径绕过；已补齐标准化处理，并用相同用例验证。限速突发测试只放入 3 个请求，其余返回 429。普通商品、商店、购物车、结账、账户、API、POST 以及 HEAD／会话 Cookie 对照均经过隔离验证。

CrowdSec 自定义筛选场景去掉了依赖爬虫自报 User-Agent 的条件，原桶容量及泄漏速度保持不变。真实引擎离线回放中，25 次／24 秒枚举从“浏览器标识不触发、爬虫标识触发”，变为两者都触发；25 次／240 秒的正常低频对照未触发。离线回放使用独立 API 接收端，没有写入生产决策。

Web Bouncer 补齐了 AppSec `deny` 故障回退的 HTTP 403 修复，并仅更新对应资源摘要。拒绝连接、超时、上游 503 三种隔离故障由原来的“HTTP 200、业务后端零命中”变为“HTTP 403、业务后端零命中”；健康和 passthrough 对照通过。**本报告 13:18 UTC 快照的 AppSec 故障策略为 passthrough；用户随后明确反对故障放行，现已改为 deny 并验证，见[策略更正及验收](2026-10-19-second-vps-appsec-failure-policy.md)。** LAPI 查询失败的原有放行行为未调整。这些故障分支不是本次筛选流量问题已证实的触发原因。

只注释了 `/etc/cron.d/crowdsec-autoupdate` 中一条重复更新命令，根用户 crontab 未修改。发行包的 `crowdsec-hubupdate.timer` 保持 enabled／active，最近执行结果成功。

发布前启动的一轮动态页面探测包含跨发布时段，四个目标均达到 18 秒超时上限；最终商品、商店、结账和账户页均返回 200。负载和响应会随流量变化，因此页面恢复不单独作为修复因果证据，主要依据是同条件的续封失败／通过及请求预算对照。

本次没有创建订单、进行支付、退款或完整登录购物验收。高峰时正常筛选也可能收到 429，其他昂贵 WordPress 路径仍需应用层优化。动态会话页面没有加缓存。FORWARD／DOCKER-USER 验证了规则接入顺序，没有执行完整转发业务流量测试。

独立 HTTP 出口与当前已建立的 SSH 管理来源重合，因此没有封禁该公网出口；Cloudflare 真实 IP 已核对，完整公网 CDN 封禁恢复循环尚未执行。网站封禁循环使用生产业务 vhost、原 WAF、实际 LAPI 和仅本地可用的临时代理入口，并计数验证后端命中。所有临时入口、信任设置、诊断放行、测试决策、命名空间和迁移快照均已清理。
