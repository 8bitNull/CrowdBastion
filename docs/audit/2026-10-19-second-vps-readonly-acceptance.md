已通过用户添加的专用 SSH 公钥登录并检查。主要发现是 WordPress/PHP 资源拥塞，以及一条有效本地封禁在 CrowdSec 防火墙集合中缺失。CrowdSec 与 Firewall Bouncer 服务正在运行，但不能据此认定防护完整有效。

证据采样为 **2026-10-19 12:23–12:27 UTC**，即服务器本地时间 20:23–20:27。各轮开始时间、命令、统计和核查范围见[脱敏证据](2026-10-19-second-vps-readonly-evidence.json)。业务域名以 site-A 至 site-D 表示，凭据及目标公网地址不写入公开报告。

## 1. 优先处理：商品筛选与页面渲染消耗 PHP 资源

服务器为 Debian 13.7、3 vCPU、约 5.8 GiB 内存。前几轮采样中，负载约为 10，`vmstat` 的间隔样本显示 CPU 空闲为 0%，无明显换页或 I/O 等待；PHP 容器一次采样占用 **273.03% CPU**。

两个 WordPress 站点共用 `www` PHP-FPM 池，`pm.max_children=10`。读取 FPM 错误日志末尾 2 MiB，在最近一小时窗口内找到 488 条慢请求告警、3 条达到进程上限的告警。相近时刻读取的慢日志末尾 2 MiB 中，site-A 的 `index.php` 占 486 个样本，site-B 占 2 个；堆栈集中在 SureCart 商品模型序列化、商品列表、WordPress 区块渲染和模板处理。

随后 12:26 轮采样已观察到 511 条近一小时慢请求告警。告警中的约 3–4 秒是触发慢日志时的耗时，不是请求完成耗时。样本包含大量 `products-order`、`products-orderby`、`products-sc_collection[]` 和分页组合。

12:24 轮采集的访问日志中，site-A 最近 15 分钟有 **1,089 条记录，其中 1,081 条为 499（99.27%）**；site-B 的 24 条记录全部为 499。499 表示客户端在响应完成前断开，不能单凭此状态认定攻击或确定全部原因。日志与进程占用支持 PHP 拥塞及跨站点影响的判断，但尚未通过受控回放证明某一插件缺陷或特定来源是唯一原因。

已有筛选防护按来源 IP 限流，并针对特定爬虫标识或地址阻断；最近 15 分钟的主站记录涉及 880 个不同来源地址，其意图未鉴定。应优先评估筛选组合限制、缓存、动态请求总并发及站点 PHP 池隔离，并继续定位 SureCart/WordPress 的昂贵执行路径。当前 PHP 请求终止超时为 0、FastCGI 读取超时为 3600 秒；调整前需确定正常业务边界。CPU 已满载时，直接增加 PHP 进程上限缺乏依据。

**末轮资源压力已回落。** 12:27 轮的一分钟负载降至 3.83，两个间隔样本的 CPU 空闲分别为 99% 和 100%；可用内存约 3.26 GiB。检查没有执行服务重启或配置修改，回落的具体触发原因未确定，不能视为修复完成。

## 2. 优先处理：一条有效封禁未进入防火墙集合

12:25、12:26、12:27 三轮均检查到 **11 个唯一的有效本地 IPv4 ban**：7 个位于本地来源集合，3 个位于 CAPI 集合，另 1 个在两类集合中均未找到。不能把位于 CAPI 集合的三个地址误报为未同步。

缺失地址的 SHA256 前 12 位为 `1132ac50536a`。12:25 轮使用 Firewall Bouncer 的有效凭据查询 LAPI，该地址仍返回一条决策、剩余约 5 分钟；12:27 轮 `cscli` 仍显示剩余 **2 分 57 秒**，集合查询仍未找到。观察跨度超过配置中的 10 秒轮询间隔。

这证明采样期间该有效 ban 未体现在所核对的 CrowdSec nftables 集合中；尚未确定原因，也没有证明该来源实际可以访问业务。未修改决策或重启 Bouncer。后续应针对有效期内的新样本，对照决策流、来源重叠与集合生命周期，再验证修复及拦截恢复。

IPv4/IPv6 的 INPUT、FORWARD 基础链与 DROP 引用均存在，优先级为 -10。静态规则、累计丢包计数及集合成员关系均不能替代独立来源的实际拦截测试。

## 3. 两套自动更新任务仍同时存在

`/etc/cron.d/crowdsec-autoupdate` 每天 03:30（服务器本地时间）执行规则更新、升级，并在前两步成功后重载 CrowdSec；系统 `crowdsec-hubupdate.timer` 也启用，其脚本在有升级输出时重载服务。

系统 timer 的上次执行结果为 success、退出状态 0，下次计划为 2026-10-20 00:04:48 CST。两套任务可合并以减少重复更新和重载窗口；本轮未停用任务，也没有将当前性能问题归因于它们。

## 4. Web Bouncer 的故障策略与版本边界

OpenResty 配置校验通过。网站 Bouncer v1.2.3 和 Firewall Bouncer v0.0.36 均有近期认证拉取记录；LAPI、AppSec、Prometheus 监听环回地址。

Web Bouncer 主配置为 `MODE=live`、`APPSEC_FAILURE_ACTION=passthrough`，未发现 `bouncer.conf.local` 覆盖。已安装源码在 AppSec 故障时按此策略继续处理；LAPI 请求失败或返回非 200 时也有独立的放行分支。

该服务器的 AppSec `deny` 回退分支仍只设置拒绝标记，没有将初始状态码 200 改为 403。因此不能直接把另一台服务器的修复状态用于本机。此项为源码核查，没有在本机注入故障或切换策略。

读取网站错误日志有限尾部，未在最近一小时过滤窗口中匹配到 AppSec 调用错误；核心独立文件日志在同窗口有 101 条 `Failed to process request body` 错误消息。请求体处理错误应另行分类，不能等同于引擎整体不可用。空的 systemd warning 查询也不能代替应用文件日志检查。
