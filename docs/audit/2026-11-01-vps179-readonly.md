## 修复与优化优先级

### 发布阻断：本地通知依赖没有完整打包

`lib/notify.sh` 的 `NOTIFY_HELPERS` 仍为 6 个文件，但新版 `crowdsec_bot_health.py` 已导入 `crowdsec_bot_runtime.py`，后者又导入 `crowdbastion_ux.py`。严格使用安装清单复制到隔离目录、排除源码路径后，`import crowdsec_notify` 实际失败：

```text
ModuleNotFoundError: No module named 'crowdsec_bot_runtime'
```

增加这两个 helper 的候选副本已通过同一隔离导入检查，且[建议补丁](2026-11-01-vps179-readonly/notification-dependencies-proposed.patch)通过 `git apply --check`。**补丁尚未应用；导入通过只验证依赖闭包，不代表安装事务和回滚已验收。** 发布前应应用修复并补“脱离源码目录的真实通知启动／配置检查”回归，再运行通知安装、失败恢复及相应全仓检查。

现有 VPS 通知使用旧的自洽副本，当前运行正常。该问题影响更新／重装通知服务，不能表述成现有通知已经损坏。此前 1392 项回归没有覆盖此次发现的独立部署导入场景，不能代替该发布检查。

证据：[原清单失败](2026-11-01-vps179-readonly/notification-import-check.json)、[候选清单导入通过](2026-11-01-vps179-readonly/notification-import-candidate.json)。

### 高优先级：消除开机整表恢复与动态规则的竞争

root crontab 第 8、9 行是启用的 `@reboot` 任务，分别恢复 `/etc/iptables/rules.v4`、`rules.v6`。同时 `netfilter-persistent.service` 为 enabled；`iptables.service` 和 `ip6tables.service` 是其**别名**，实际只有一个服务，不应当作三个独立服务重复操作。

两份保存规则均不含 CrowdSec 链，且包含旧 Docker 规则。恢复它们会替换整表内容；如果发生在 Docker 或 Bouncer 建链之后，可能移除动态保护入口。当前入口完整不代表下次启动没有竞争，也未证明过去某次故障确由此造成。

排除 Docker／CrowdSec 行并归零计数器后，保存文件与当前静态部分一致：IPv4 还有 1 条静态规则，IPv6 为 0。IPv4 规则是 `INPUT -i lo -p tcp --dport 81 -j DROP`。因此不能简单删除所有持久化文件；应先确认该规则是否仍需保留，并为需要的静态策略确定只管理自身规则的启动方式，再停用两条旧整表恢复 cron 和对应服务的自动启用。停用操作应避免顺带执行可能改变当前规则的 stop／flush，且不触碰其他 cron。

新检查器已实测报告启动覆盖风险；旧终端 `--status` 未提示这个风险。证据：[health.json](2026-11-01-vps179-readonly/health.json)、[followup.json](2026-11-01-vps179-readonly/followup.json)、[规范化比较](2026-11-01-vps179-readonly/final-probes.json)、[静态规则摘要](2026-11-01-vps179-readonly/static-rules.json)。

### 高优先级：让终端和机器人使用同一健康检查

现场复现了两个不同结论：终端 `--status` 返回 2，显示“运行检查通过，实际拦截待验证”；已安装机器人 HealthCollector 则返回 `logs=fault`，提示日志已读取却未解析。其原因包括轻量检查将全部来源一起判定，而终端 HTTP 检查按适用来源判断。

具体指标中，`proxy-host-19_error.log` 的 3 行全部未解析；补查内容类型均为 Nginx “buffered to a temporary file” 的 warn。`fallback_error.log` 还有历史未解析计数，但当前文件已空，无法从当前文件复原当时内容。多个网站 access 日志持续有成功解析，两个 Nginx 解析器也已启用。因此不能把机器人摘要当作所有网站日志失效的证明，更不应直接重装解析器。

更新机器人及其独立 manager/lib 后，用 `--status-json` 与机器人重新对照 required、scope 和 summary。由于开机覆盖风险是真实存在的，新版完整检查在修复前报告异常是预期结果，不能为了“绿色”而忽略它。通知服务仍只监测其已定义的组件范围，不应把交互机器人的完整健康结论扩展为通知服务的覆盖承诺。

### 高优先级：明确 NPM 管理端口的访问范围

81 端口在 IPv4／IPv6 所有地址监听，NPM 的 Node 后端 3000 也监听所有地址；`docker top` 确认该 Node 进程属于 NPM。现有唯一静态规则只丢弃 lo 上的 81 流量，不能限制公网来源，反而可能阻断转发到 `127.0.0.1:81` 的 SSH 隧道。

建议根据管理方式选择可信来源限制、VPN 或本地访问策略，并同时核对 IPv6 与 3000 后端；采用隧道前要处理现有 lo DROP。当前没有发起公网探测，也没有读取云侧防火墙策略，**这里只确认监听与本机规则，未宣称公网一定可达**。80／443、SSH 53322 及 realm 业务端口应按实际用途分别保留。

### 常规优化：固定发行与镜像，保持更新边界清晰

管理代码统一到完整、带指纹的发行目录，避免只换主脚本而留下旧 lib。源码、cron 托管副本、交互机器人、独立通知是分别更新的对象。当前 CrowdSec 自动更新 cron 未启用，更新代码时保持这个选择，不能顺手启用新的定时任务。

NPM 使用 `jc21/nginx-proxy-manager:latest`，本次运行镜像 digest 为 `sha256:4393e642e233e5efd5adeb7f10918d4aaea71c9ed875b94190273fc8e87f9594`。后续可固定已验证版本／digest，并记录对应备份；本次脚本更新无需同时拉取 NPM 镜像。

## 建议更新顺序与验收条件

1. **先修本地发布候选。** 应用通知依赖补丁，加入独立打包回归，完成相关安装／回滚测试与最终验证；生成本次候选的完整源码清单。当前工作树尚未提交或推送，部署包必须来自被验证的工作树，不能只取 HEAD。
2. **建立一致的私有备份。** 保存日常入口及完整 lib、旧发行目录路径、各 unit／drop-in、root cron 和恢复机制配置、`/etc/crowdsec` 的配置原文、角色／托管资源记录、机器人 offset／审计和通知队列的恢复点。记录程序权限、链接、enabled／active 意图及镜像 digest。活动数据库用一致性备份；不能把运行中的 SQLite 文件随意复制成可恢复性保证。
3. **暂存完整新发行目录并只读预检。** 校验所有文件、归属与权限，运行帮助和 `--status-json`。取回的健康报告必须能被新版 reader 验证，且单次检查要满足机器人 20 秒预算；旧现场 `--status` 约 9.36 秒不能代替新版完整检查的实际耗时测量。预检不得调用安装、迁移或发送消息的入口。
4. **处理旧规则恢复归属。** 先安置需要保留的静态策略，精确停用两条 root 恢复任务及单个持久化服务的自动启用。保持当前动态规则，立即复查双栈入口和静态部分，再复查开机审计；冷启动验证另选维护窗口。
5. **切换日常管理入口。** 以能执行真实发行脚本的包装入口切换，保留旧兼容入口；不要只把主脚本链接到另一目录却继续从旧位置加载 lib。此次不升级 CrowdSec 软件包、不迁移已正常工作的后端、不拉取 NPM 镜像。
6. **单独更新交互机器人。** 使用新版“代码检查／保留配置更新”流程，部署完整 helpers 和自包含 manager/lib。当前服务 active／enabled 属于支持状态；预期有短暂轮询中断。比较机器人配置更新前后的原始字节，保留 offset、审计与通知状态；确认只有一个轮询实例。
7. **按需要单独更新通知。** 可以继续使用当前 ready 的旧副本。如果选择更新，必须采用已修复依赖的完整清单，保留目标、策略、密钥和队列；只做本地配置／心跳检查，Telegram 实际投递另行验收。
8. **收尾复查。** 管理入口和机器人 manager/lib 指纹一致；终端与机器人同次检查的范围、必检项和结论一致；服务意图保持；双栈入口完整；决策入核无遗漏；网站配置有效；机器人轮询与通知心跳新鲜、无持续重试。结果应区分“运行检查”“开机配置审计”和“外部真实阻断”。

## 回滚方案

- **代码／机器人失败：** 恢复修改前的管理入口、完整程序和 helpers、unit／current 指针及原服务意图。新版机器人更新事务会尝试恢复失败或 INT／TERM 中断，但仍需现场验证恢复结果。
- **通知失败：** 独立恢复通知程序、unit、路由和配置，保留可继续投递的队列；不要把交互机器人回退当作通知回退。
- **启动策略调整失败：** 根据备份恢复相关 cron 与单个持久化服务的启用状态，但这会重新引入已发现风险；保留明确说明。不要为了回滚而在运行中的 Docker／Bouncer 上直接恢复整张旧规则表。需要恢复的静态规则应精确处理，随后重新检查动态入口。
- **状态保留：** 常规代码回滚不回退已推进的 offset、已发送标记或通知队列，避免重复处理；状态损坏才进入单独的一致性恢复。配置按原文恢复，凭据不得写进公开报告。
- **失败边界：** SIGKILL、断电、主机故障以及软件包整体安装不在文件事务完整回滚承诺内。下次重启后的保护顺序与真实外部阻断尚未验收。
