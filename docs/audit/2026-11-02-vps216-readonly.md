## 优先处理：旧规则仍可能经 systemd 恢复

原 root `@reboot iptables-restore` 任务仍为注释状态，但 **netfilter-persistent.service 为 enabled、active (exited)**。`iptables.service` 与 `ip6tables.service` 的 `Id`、`Names`、`FragmentPath` 和启动记录表明它们是同一个 unit 的别名，不能算成三套独立任务。

两个插件会分别对 `/etc/iptables/rules.v4`、`rules.v6` 执行 restore；脚本有可选 NOFLUSH 分支，当前 defaults 只显式设置 `FLUSH_ON_STOP=0`。IPv4 快照 44 行，含 raw、mangle、filter、nat，**CrowdSec 相关行数为 0**，且有历史 Docker bridge 引用；IPv6 快照为空。服务在 11 月 1 日启动时早于当前 Docker 和 Bouncer，当前动态路径已正常建立。这里确认的是旧整表恢复入口及其覆盖风险，**没有证明当前已经发生规则被覆盖，也没有重新加载旧快照复现**。

建议下轮先核实并保留需要跨重启的静态策略，再取消这个旧整表恢复机制的开机执行，同时保留规则快照供人工审计。不要把启动风险处理等同于在生产执行整表 restore、flush 或无准备地停止相关服务。本轮没有执行任何这类操作。

## 采集结果应按来源解释

网站 access.log 已读取并解析 **590 / 590** 行；auth.log 读取 199 行、解析 73 行、未解析 126 行，已有有效 SSH 解析证据。通用 syslog 则读取 **18,294 行、解析 0 行**，因此当前仓库共享全量分类器如实返回 `fault`。这和旧版网站、V2bX 简版诊断返回“运行检查通过，实际拦截待验证”（exit 2）的范围不同，不能抹去该异常，也不能由此断言网站或 SSH 检测全部失效。

采集配置显示 syslog 与 auth.log 均使用 syslog 标签；额外读取的 syslog 末 256 KiB 样本有 1,067 行，均为 ISO8601 时间格式，主要来自 V2bX（792）与 systemd（272）。这只能说明该段样本的内容，**不足以认定 ISO8601 格式就是零解析的根因**。建议核对 syslog 采集用途、时间格式及解析器覆盖，再决定修正、缩小范围或按需保留，不应只为使摘要变绿而关闭必要来源。

## 网站与 V2bX 的实际防护边界

这台使用 `nginx:alpine`，host 网络。有效配置没有 Lua access hook 或 CrowdSec Web 安装登记，AppSec 引擎指标为空：当前已有 Nginx 日志检测与主机来源 IP 防火墙封禁，**尚未配置请求级 Lua Web Bouncer／AppSec**。正常首页 200 不证明请求级攻击拦截；本轮没有更换镜像或增加拦截组件。

有效 Nginx 配置包含 `X-Forwarded-For`，本次扫描未发现 `set_real_ip_from 0.0.0.0/0` 或 `::/0`；并未逐站、逐入口验证访客 IP 信任链。源站检查通过 loopback、`--resolve` 和 `--insecure`，公网首页请求正常校验证书；公网首页可用不证明真实来源识别或阻断。

V2bX 配置可读取，声明 sing / AnyTLS，当前有归属 V2bX 进程的 TCP 8443 监听。检查器仍将节点与监听映射、来源透传、协议版本及实际封禁效果记为未验证；共享 journal 候选未匹配到专用 CrowdSec 采集，专用持续观察与告警未验收。因此现有来源 IP 规则不等于已经具备 AnyTLS 专用攻击识别或端到端业务拦截验收。没有主动建立代理业务会话、发送攻击或启用观察服务。
