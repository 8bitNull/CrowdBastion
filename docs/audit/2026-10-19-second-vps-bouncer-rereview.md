## 1. 商品筛选规则存在明确的覆盖限制

本机自定义场景 `local/aomway-shop-filter-crawl` 要求 User-Agent 匹配 `(?i)(bot|crawler|spider)`，然后按来源 IP 聚合不同的筛选 URI；桶容量为 20，每 5 秒泄漏一个事件。Nginx 另有针对商品筛选的每 IP `1r/s` 限流，并只对特定爬虫标识或地址直接拒绝。

在 12:34:02 UTC 为终点的最近 30 分钟访问记录中：

| 项目 | 结果 |
| --- | ---: |
| 商品筛选访问记录 | 4,395 |
| 日志中的不同来源 IP | 4,242 |
| 不满足上述 User-Agent 条件 | 4,328（98.48%） |
| 满足上述 User-Agent 条件 | 67，涉及 12 个 IP |
| 单 IP 每分钟最多的筛选记录 | 6 |
| 客户端状态 | 4,199 个 499、106 个 200、89 个 503、1 个 403 |

该 User-Agent 条件是场景 filter 中的必要条件，因此不满足的记录无法进入这条自定义场景。其余 67 条仅满足这一项，不代表满足全部解析和场景条件。来源分散、单 IP 记录少，也与现有按 IP 的阈值不匹配。

这能解释昂贵的筛选请求为何可能持续进入 PHP，同时没有触发这条规则。结合上一轮 PHP 慢日志，优先方向应为限制筛选组合成本、缓存、站点及动态请求并发预算，再评估检测规则；仅删除 User-Agent 条件仍无法解决大量来源各发少量请求的情形。

这些访问不是已标注的恶意请求样本，访问日志的完成时间也不等于请求到达时间。不能将全部 4,395 条都定为攻击，或把全部 499/503 都归因于 CrowdSec。

## 2. 网站 Bouncer 的接入记录完整，但仍需外部请求验收

托管安装记录显示为 `installed`、`1panel` 模式，目标配置摘要与记录一致，26 个资源文件全部匹配，没有发现资源丢失或摘要变化。当前 Nginx 磁盘配置只有一个受管理的 access Lua 钩子，未发现 `satisfy any` 或 `$crowdsec_*` 覆盖变量。LAPI allowlist 查询为空；管理员解析白名单为环回和私有／CGNAT 网段，未发现全公网通配放行。

配置使用 `CF-Connecting-IP`，信任 22 个代理 CIDR，没有 `0.0.0.0/0` 或 `::/0`。对经过 Cloudflare 的流量，源站防火墙匹配连接对端，恢复后的访客 IP 需要由网站 Bouncer 判定。因此必须分别验证主机防火墙和网站访问层。

以上仍是磁盘配置和安装记录核查，不代表读取了现有 worker 内存，也不能替代来自独立设备的真实 IP、封禁与恢复对照。原 1Panel WAF access 文件为编译内容，本轮未能进行其源代码审阅。

这 18 条记录早于上轮 12:25–12:27 的集合缺失窗口，不能用来证明该缺失窗口中的请求行为。当前该旧决策已到期，剩余 10 个有效本地 IP 在 CrowdSec 或 CAPI 集合中均可找到，**10/10 不代表此前的缺口已修复**。

## 4. 故障放行和安装版本仍需纳入整改

本机 Web Bouncer 为 `live` 模式；AppSec 故障策略是 `passthrough`，LAPI 查询失败也有独立放行路径。已安装的 AppSec `deny` 回退分支仍缺少当前安装器已有的 403 状态修正。安装资源与旧记录一致，不能据此认为已获得当前脚本中的修复。

本轮对各网站错误日志最多读取末尾 8 MiB，在最近 24 小时过滤窗口中未匹配到 AppSec/LAPI 调用失败、Bouncer error 或 Lua runtime 中止记录；不是完整历史保证。因此目前没有证据将本次筛选流量问题归因于这些故障分支。切换拒绝策略前，应先验证故障返回状态和正常业务的可用性。

## 建议的处理顺序

1. 优先控制昂贵商品筛选请求的总成本及并发，补充缓存和正常购物对照；评估仅按 IP、依赖爬虫自报标识的规则覆盖范围。
2. 复核封禁同步生命周期，并用独立测试来源和正常对照来源验证“可访问 → 封禁 → 恢复”，同时关联网站 Lua 判定与后端请求。
3. 按备份和回滚流程补齐已确认的 Web Bouncer 修复，合并重复更新任务，再选择符合业务可用性要求的故障策略。

本轮两次读取的 4 个关键文件摘要一致，CrowdSec 和 Firewall Bouncer 的 PID 及零重启计数保持不变。没有安装或部署新版本，没有进行故障注入或真实封禁操作。
