# Nginx worker 重生误报修复与复审

修复策略修改及托管模块升级的重载误报：master 拒绝 Lua 初始化后，全部旧 worker 崩溃并被原配置自动重生，会产生稳定的新 PID，却没有加载所选策略。真实双 worker Nginx 与官方 Lua 回归先确认旧实现返回成功、磁盘为 `deny`，而 HTTP 读取的 worker 内存策略仍为 `passthrough`；修复后返回失败、恢复原配置，不输出成功提示。

## 成功证据

保留同一 master、完整新 worker 集合连续两次存活及托管钩子检查；另外要求捕获日志游标之后，同一 master 依次记录 `reconfiguring`、完整的 `start worker processes`，以及与当前 worker PID 对应的启动记录。单个 worker 自动重生的 `start worker process PID` 不构成成功证据。后续初始化拒绝、再次重载及冲突的生命周期事件使此前证据失效。

日志来源由有效配置的主文件直接声明与 master 实际打开的文件描述符共同核对。验证期间持有原 inode，记录偏移及前缀摘要，拒绝旧记录、截断覆盖、替换文件及超出 1 MiB 的新增日志；只解析完整记录。所有日志查询有超时，重载后查询共享原有单个 10 秒观察期限。

通过 `/proc` 的 `NSpid` 对应宿主机和容器日志 PID。独立复审进一步发现两个容器可能共用同一日志、各自 master 都显示 PID 1，因此新增归属检查：定位日志、捕获游标及接受结果时，拒绝另一个相同日志 PID 的进程持有同一 inode，防止其他容器的成功记录混入本次结果。

## 运行前提

自动验证要求主配置直接声明绝对路径、普通文件类型的 `error_log ... notice;`，并提前由实际 master 正常加载；`info`、`debug` 级别也可。stderr 已重定向至普通文件时可以核对。stderr 管道、syslog、隐式默认日志、相对路径、仅在 include 中声明、元数据不可读及日志归属不明确时，返回未确认并执行现有回滚，不自动修改网站日志配置。请参见[操作前提](../appsec-guide.md#正文与故障策略)。

## 验证及复审

最终定向回归 **118 项全部通过，无跳过**，耗时 171.994 秒。其中包含 18 项真实 Nginx/Lua 测试。新增用例覆盖重载拒绝后旧配置 worker 重生、不可观察日志、日志查询挂起、旧记录、完整记录边界、容器 PID 映射、共享日志身份冲突、日志替换/截断及读取预算。

回填后原工作区完整回归 **1026 项：1005 通过、21 跳过、0 失败**，耗时 370.351 秒；18 项真实 Nginx/Lua 测试全部通过。跳过的是既有可选 gost、官方 CrowdSec 通知插件/回执及 ISO 媒体验证依赖。仅回填本轮 10 个文件，保留并行改动、原分支及入口软链接。

项目静态检查通过：26 个 Bash 文件语法，隔离目录 185 个、原工作区 193 个 Python 文件 AST，重载模块 ShellCheck 0.11.0 及差异空白检查。独立只读复审发现的共享日志问题已补充 RED/GREEN 回归并修复；最终复审未发现其他实质问题。结构化证据、文件摘要及完整回归记录见[验证结果](2026-10-20-nginx-respawn-fix-results.json)。

本轮未连接 VPS；Docker 命令和 systemd 元数据由 fixture 提供，Nginx master/worker 与 Lua 使用真实进程。检查证明当前观察窗口内的配置接受及 worker 更替，仍需部署后进行正常业务和故障请求验收。
