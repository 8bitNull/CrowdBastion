# 2026-10-19 Bouncer 第二轮复审

复审发现了此前未核对到的生产线索：AppSec 调用确实发生过失败，当前策略允许失败后继续处理；相关访问日志中存在上游与客户端均返回 200 的记录。此前的受控 IPv4／IPv6 INPUT 封禁测试仍成立，但不能据此判断网站不存在漏防。

本轮仅执行远程只读检查和本地证据整理，没有新增封禁、编辑生产配置或重启服务。证据采集时间为 11:20–11:31 UTC，详见 [脱敏证据](2026-10-19-bouncer-rereview-evidence.json)。

后续只读调查已将两次 AppSec 连接拒绝定位到重复自动更新引起的重载窗口，并整理了首个调度清理建议，见 [后续定位与改动建议](2026-10-19-appsec-followup.md)。下文保留本轮采集时的计数与结论。

## 1. 重要：生产 AppSec 失败与继续回源的关联记录

对 33 个 NPM 错误日志各读取最多末尾 256 KiB，找到 **138 条** `AppSec check` 错误，全部可解析时间，发生在 **2026-10-19 05:51:42–11:00:12 UTC**：

| 错误类型 | 记录数 |
| --- | ---: |
| timeout | 137 |
| connection refused | 1 |

磁盘配置为 `APPSEC_FAILURE_ACTION=passthrough`。已安装的 `crowdsec.lua` 在 AppSec 调用失败时返回此策略指定的放行结果，调用者记录错误后继续处理。

库支持 `bouncer.conf.local` 覆盖主配置；11:31 UTC 补查确认宿主机和容器内均没有该覆盖文件，主配置所选选项与此前读取一致。Nginx 配置展开中也没有 `$crowdsec_*` 变量引用。这些检查补足了配置覆盖项核对，仍不读取现有 worker 的内存状态。

进一步将错误记录与访问日志按同一站点日志、客户端、Host、方法、原始 URI 及时间关联。检索窗口为错误后 0–15 秒，要求每个错误只有一个候选响应、每个响应也只有一个候选错误；反向候选数包含所有候选边，排除歧义记录。取得 **78 组关联**，实际时间差均为 0 或 1 秒：

| 客户端状态／上游状态 | 关联数 |
| --- | ---: |
| 200／200 | 31 |
| 404／404 | 42 |
| 301／301 | 2 |
| 302／302 | 1 |
| 405／405 | 2 |

31 组 200／200 包含 30 次超时和 1 次连接被拒绝。示例包括 `proxy-host-12` 在 **11:00:12 UTC** 的连接被拒绝，以及 `proxy-host-19` 在 **06:42:16、09:21:00 UTC** 的超时；对应访问记录的上游状态均为 200。

这些数据支持“未取得成功 AppSec 检查结果时，请求仍可能继续回源”的判断，并将此前单纯的配置风险推进到了生产日志证据。日志没有统一请求 ID，关联不能替代逐请求追踪；超时也不能证明引擎完全没有处理请求。不能仅凭这些记录认定请求有恶意、攻击成功，或来源当时已有有效 ban。

本轮未确定超时和连接被拒绝的根因，不能将其直接归因于内存、CPU、网络或服务重启。空的超时配置采用已安装库的默认值：连接 100 ms、发送 100 ms、处理 500 ms；这些数值本身不能证明配置不当。

## 2. 网站决策查询还有独立的失败放行路径

读取已安装的 Lua 库，确认 `plugins/crowdsec/live.lua` 的 LAPI 请求失败和非 200 响应分支均返回允许；`crowdsec.lua` 记录错误后继续执行独立的 AppSec 检查。若 AppSec 返回允许，Web 层可能无法执行当次未成功取得的已有 ban。

这是安装源码中可确认的行为。所查错误日志尾部没有匹配到 LAPI 查询失败或 Bouncer error，因此本轮没有取得该分支在生产中触发的日志证据。**修改 `APPSEC_FAILURE_ACTION` 不能直接改变 LAPI 查询失败的处理方式。**

另有一项短时窗口：`MODE=live`、`CACHE_EXPIRATION=1`，无决策结果会缓存约 1 秒。新增 ban 可能等待原有允许缓存过期；这不足以解释持续漏防。Web live 查询的缓存与 Firewall Bouncer 的 `10s` 轮询属于不同机制。

## 3. 切换失败策略前需核验的源码问题

静态检查发现，`crowdsec.lua` 的 AppSec 失败处理先将回退状态设为 200，进入 `deny` 分支时只修改允许标记及处置类型，没有同步修改状态；错误返回随后把该状态传给 `ban.apply`，后者接受传入值。若改为 `deny`，可能出现“返回封禁页但 HTTP 状态为 200”的情况，影响监控和状态码判定。

当前 `passthrough` 不进入该拒绝分支。本轮没有切换策略或执行故障注入，因此该项属于源码发现，不能解释上文的上游 200，也不能称为已复现的生产拒绝故障。

## 4. 上轮结论复核与覆盖边界

独立审阅核对了上轮探测脚本、SHA256、原始结果、事件记录与公开证据，未发现推翻受控 INPUT 测试的错误：测试前后测试／对照来源均可用，封禁期间仅测试来源全部超时；集合成员和 IPv4／IPv6 各增加 5 包的计数相符；撤销与恢复发生在两分钟有效期内。该测试仍只证明所测本机 INPUT 新连接，未覆盖公网／CDN 请求、FORWARD、既有连接、realm 应用及 UDP 转发或自动攻击检测。

修正了上轮报告的配置措辞：`nginx -T` 检查并展开磁盘配置，不能单独证明现有工作进程已加载相同版本。当前展开的 22 个代理站点均包含受管理的 server 级真实 IP 配置，信任 22 个 Cloudflare CIDR 并使用 `CF-Connecting-IP`；未发现独立 access Lua 覆盖或 `satisfy any`。这仍是静态检查，不能替代真实 CDN 请求核验。

NPM 的强制 HTTPS 跳转使用 rewrite 阶段的 `return 301`，早于 access Lua。单独收到这类跳转不能证明访问到了业务后端。上文的 31 组 200 另行核对了上游状态，未把跳转或仅有访问日志当作成功回源。

本轮也扩大了当前本地 IP ban 的日志核对：33 个访问日志每文件最多末尾 1 MiB，共读取约 4.15 MB、16,930 行，其中 539 行未按目标格式解析。在最近 24 小时过滤窗口内，9 个当前本地封禁地址有 478 条历史请求，但没有取得其决策创建后超过 120 秒的合格请求样本。因此仍不能确认或排除“ban 已生效却能访问”的具体事件。该检查不包含 CAPI 全量列表、范围决策、已过期历史 ban 或归档日志，也不代表完整 24 小时覆盖。

## 后续处理优先级

1. 优先调查 AppSec 超时和拒绝连接的原因，并对失败数量、延迟设置监测；当前日志已证明调用失败实际发生过。
2. 按业务可用性要求评估失败时放行或拒绝的策略；变更前验证返回状态及是否回源，检查上述 200 回退问题。独立评估 LAPI 失败行为。
3. 对用户怀疑的具体事件核对 IP、时间、域名／端口与当时决策；公网或 CDN 路径仍需相应受控来源，现有 INPUT 测试不能替代。
