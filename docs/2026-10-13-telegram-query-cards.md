# Telegram 查询卡片与实际拦截证据

本轮优化自定义交互机器人，官方自动通知继续负责推送。封禁名单和站点体检均为用户发起的只读查询。

## 封禁决策

使用 `cscli decisions list -l 50 -o json` 的告警数组，读取其 `decisions`；`-l` 限制的是告警数量，不能视为决策总量。沿用 CLI 默认来源范围，不包含 CAPI。页面注明查询范围与本次结果，不能代替全局封禁统计。

按 `(scope, value)` 分组，每页 5 个目标；保留每条决策，详情每页 5 条，展示规则、来源、类型、剩余时长、模拟状态与告警 ID。首页显示第一条决策，重复项提示查看详情；解封和日志解析白名单入口位于 IP 决策详情，均需确认。Range/CIDR 不提供 IP 解封或加白按钮；IP 解封明确删除该 IP 的全部决策。取证按钮读取告警事件与 ASN/归属信息；这些历史告警附带的决策不应替代当前有效决策列表。取证卡片可按来源 IP 重新查询当前决策，查询范围仍受上述来源与告警数量限制。

翻页、刷新及返回列表编辑原消息；每次重新查询，决策过期或新增时排序和页数可能改变。消失的目标说明可能过期或超出查询范围。查询失败与空结果分开报告，字段 HTML 转义并限制展示长度。

## 站点体检

九宫格入口现名为“容器状态”，兼容旧“站点体检”入口。每页 5 个 Docker 容器，包含停止的容器。展示运行状态、Docker 状态摘要、HEALTHCHECK 和启动时间；未配置 HEALTHCHECK、状态查询失败均明确报告。只读取摘要和 `.State`，不展示完整 inspect、环境变量或密钥。

按 CrowdSec 配置文件所在目录读取 `crowdsec-1key-web-installs.json`，对选中容器的主配置文件计算 SHA256，与安装记录比较。此检查仅证明主配置文件指纹一致，未检查容器挂载、Bouncer 资源文件或运行时加载。不在记录中的容器显示“无本工具安装记录”，不推断没有外部 Bouncer。其他接入方式尚未核验。HTTP 可用性显示“尚未验证”，首版不访问业务 URL。

## 如何验证 Bouncer 实际拦截

2026-10-19 新增 Web 执行证据采集和查询。官方自动通知可能在执行决策前送出，因此推送仍说明尚未核验，并提示使用 `/inspect` 调阅告警，再点击“执行核验”；核验卡上的“刷新”会重新查询并编辑原消息。回执从升级后的新请求开始生成，历史请求不会补录。

托管 Lua Bouncer 在执行 ban 时标记原因，在请求结束的 log 阶段确认最终状态为预期的 4xx/5xx，且没有业务 upstream 地址，再记录带服务器生成 request ID 的回执。原因区分 LAPI ban、LAPI 故障拒绝、AppSec 规则拒绝、AppSec 故障拒绝和请求体读取失败拒绝；已有故障策略保持不变。1Panel 原有 log hook 保留并先执行。业务自身返回的 403 不会作为 Bouncer 回执，客户端请求头里的 ID 或标记也不会直接成为执行证据。

查询卡把“当前 LAPI 决策”和“Web 执行观测”分开显示：

- **已观测到拒绝**：所选 IP 和时间窗内存在可信 Web 拒绝回执，展示原因、数量、最近时间、响应状态和服务器 request ID。
- **尚未观测到**：本次可读日志范围内没有匹配记录；不表示拦截失败，也不表示来源安全。
- **读取不可用**：日志缺失或读取失败，不能据此判断执行结果。若扫描受限或部分文件读取失败，卡片会注明。

默认读取 NPM 日志目录；自定义机器人 JSON 配置可用 `execution_log_dirs` 指定 1–4 个绝对目录。读取当前及 `.1` 轮转的 error 日志，最多扫描 128 个文件，每个文件尾部 64 KiB，总上限 8 MiB，时间窗最多 24 小时。拒绝符号链接，只接受执行模块对应的 Nginx 日志格式，并验证 IP、时间、状态、upstream 和 request ID。结构化回执和 TG 卡片不包含 URI/UA/密钥；现有 Nginx error 日志机制会在整行末尾附加请求上下文，可能含 URI，须沿用敏感日志的访问权限。

本期覆盖托管 Web Lua Bouncer 的 ban 4xx/5xx；重定向、验证码/挑战和防火墙 DROP 不在证明范围内。同 IP、同时间窗只证明该来源曾被拒绝，**不能证明原触发请求或某条告警决策实际被执行**。日志型检测产生决策时，触发请求可能已经到达后端，决策只影响后续请求。模拟告警也只能作为独立来源观测的查询入口。

若要进一步证明某个指定请求在完整入口链路被拦截，还需要：

1. 从专用外部测试客户端请求明确授权的测试 URL，携带唯一探针标记。先确认正常请求能到达后端，保留真实来源 IP、UTC 时间、方法、路径和 UA。避免用 VPS 自身或管理连接作为封禁来源。
2. 在实际入口记录服务器生成的 request ID、经过可信代理链解析的真实来源 IP、方法/URI、时间，以及 Bouncer 明确的 deny/ban 执行结果。不能直接信任客户端传入的请求 ID；日志仅有 HTTP 403 时，无法排除 CDN、业务或其他 WAF 拒绝。
3. 检查后端在同一标记与时间窗内没有收到请求，并确认后端日志正常工作且正常对照请求已记录。若是 Firewall Bouncer，入口 HTTP 日志通常不存在，应使用来源/目的地址、协议和端口关联防火墙 trace/对应 DROP 规则计数与后端证据。
4. 将执行记录关联到相同告警及请求，保存组件、执行时间和证据引用；只有匹配成功的请求可显示“已验证 Bouncer 拦截”。聚合告警有多个请求时，应标明验证的样本和数量，不能用一次成功测试认定整个告警都被拦截。

受控链路验收与生产告警验证是两个结果。隔离 OpenResty/Bouncer 测试通过实际 HTTP 响应和后端请求数验证回执，但不证明某条生产告警。服务 active、Bouncer 最近拉取时间、配置一致、有效决策、累计计数和真实 IP 验证记录都不能单独作为该请求的执行回执。该功能不自动发起攻击或外网探针。

## 更新已有机器人

在 VPS 更新完整项目后执行：

以下目录为新检出的示例；已有安装请进入原项目目录，更名不要求移动目录。

```bash
cd /home/CrowdBastion
git pull --ff-only
sudo bash crowdbastion.sh --custom-bot
```

选择 `1. 配置/更新并启用`，安装器更新托管文件并重启 `crowdsec-1key-bot.service`。请保留原 Token、Chat ID、管理员 ID 和路径配置。仅重启服务不会把仓库新版复制到安装路径。若实际运行的是自行部署的 `/usr/local/bin/crowdsec_bot.py`，先按原文档识别和停用它的真实启动入口，再迁移；不要猜测 `crowdsec-bot.service` 一定存在。

执行证据还需要更新托管 Web Bouncer：在原安装入口选择对应容器，已有托管安装会核验挂载与文件归属后升级 log hook 和记录模块，检查并重载 Nginx；遇到未知文件修改会拒绝覆盖。只更新机器人不会让旧 Web Bouncer 自动产生回执。机器人重启不再发送“已上线”消息。
