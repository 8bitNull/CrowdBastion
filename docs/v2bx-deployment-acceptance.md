# V2bX 混合入口部署验收

本流程用于将现有离线观察结果推进到实际 VPS 验证。当前仓库没有目标 VPS 连接信息、真实 V2bX 日志或入口来源证据；以下表格是待执行清单，不能作为已通过的报告。

## 先取得本机诊断

在实际落地 VPS 的项目目录运行，按实际配置路径和 unit 修改参数。不要把开发容器的输出当作落地证据。

```bash
sudo bash install-crowdsec-1panel.sh --diagnose-v2bx
```

需要 JSON 时调用同目录 helper：

```bash
sudo python3 lib/crowdsec_v2bx.py \
  --config /etc/V2bX/config.json --cs-dir /etc/crowdsec \
  --unit V2bX.service --json
```

已核实节点入口后，可加 `--entries '1:mixed,2:relay-proxy'`；编号为 Nodes 数组顺序，上例仅适用于实际有这两个节点且路径吻合的情况。动态面板下发的端口和传输仍需操作者补充，不从 socket 猜测节点对应关系。

诊断返回 `2` 表示已输出报告但业务保护未验证；`1` 表示输入或关键查询失败，需先处理。不能用 `|| true` 将失败计为通过。诊断仅展示固定字段，但主机与来源地址仍属于部署信息，分享前确认保留范围。

若由代理直接连接 VPS，提供已有 SSH 主机别名及其角色（落地/中转/中心）、实际配置路径、服务 unit，以及可用的受控测试客户端即可；不在聊天中发送密码、私钥、面板密钥或 Bouncer 密钥。现有凭据应通过已经配置好的 SSH/密钥管理方式使用。

## 建立实际路径清单

每个已部署协议、传输、IPv4/IPv6 和入口路径各记一行。未部署组合标记“不适用”；缺少证据标记“未验证”，不默认通过。

| 字段 | 需要记录的证据 |
| --- | --- |
| 部署版本 | V2bX 当前运行版本、构建来源、实际 core 版本；历史启动行仅作候选 |
| 节点映射 | Nodes 顺序编号、内核、协议、TCP/UDP、端口和入口路径；不记录用户 UUID/密码 |
| 测试身份 | 独立受控客户端的出口 IP；与管理员及中转出口分开 |
| 中转实现 | 实际软件/版本、TCP/UDP 转发方式、是否 SNAT、是否传递可信来源元数据 |
| 三处来源 | 用户出口、日志 source_ip、落地接收数据包源 IP；代理中转还需入口接收源 IP |
| 事件关联 | 测试起止时间、一次新连接、对应日志分类；不能仅凭同 IP 和累计计数关联 |
| 执行位置 | 哪台机器的哪条链可见拟封禁用户 IP；本地监听与路由转发分别核实 |
| 测试状态 | 成功、失败、不适用、未验证；普通错误与认证失败分别记录 |

来源判定按以下对照执行：

| 路径 | 需要看到的证据 | 通过后可能的执行位置 |
| --- | --- | --- |
| 直连 | 日志来源与落地包源均为受控客户端出口；无额外代理重写 | 落地，按实际链核验 |
| 保源中转 | 经中转建立的新连接，落地包源仍为客户端出口；中转/回程路径已核实 | 落地，按实际链核验 |
| 代理/SNAT 中转 | 落地包源为中转；入口包源为客户端；失败事件有可信的客户端归因 | 可见客户端包源的中转入口 |
| PROXY 元数据 | 日志可能为客户端，但落地包源仍是中转；还需确认受限入口与协议支持 | 不能凭日志元数据在落地阻断客户端 IP |
| 同端口混合 | 每条直连/中转路径分别完成以上对照；记录中转全部 IPv4/IPv6 出口 | 各路径分别决定，不能凭一次测试统一决定 |

VPS 本机可用已有网络诊断工具短时查看指定测试入口的包头。只观察自己的测试客户端和明确端口，记录数值源地址、端口和时间即可，不导出业务载荷或全量 pcap。TCP 需使用新连接；UDP 要核实连接跟踪及回程，不能用 TCP 结果代替。客户端经 NAT 时记录其实际出口，不能预期防火墙识别 NAT 后的单个用户。

`--relay-path` 和 `--relay-status` 可补充规则引用与路径声明，但不能替代本步骤的数据包证据。中转的应用层代理入口通常经过 INPUT，路由转发可能经过 FORWARD；具体取决于实际实现和容器网络。

## 在本机核查真实日志

按 [日志指南](v2bx-guide.md#日志样本离线核查第二阶段离线部分) 使用最近、有界的文件样本或 journal JSON。先在本机形成投影报告，原始日志保持本地；不要发送完整配置、UUID、账户标签、访问目的地址或原始错误链。

以 journal 的相对计时日志为例，实际 unit 需一致：

```bash
sudo sh -c 'umask 077; journalctl -u V2bX.service -n 200 --no-pager -o json > /root/v2bx-journal-sample.jsonl'
sudo python3 lib/crowdsec_v2bx_logs.py \
  --file /root/v2bx-journal-sample.jsonl --core sing --unit V2bX.service
```

有中转来源时必须加 `--relay-cidrs`，填实际网段或 `/32`、`/128` 单地址，不能照抄文档示例。xray 文件日志还需 `--timezone` 填事件发生时的实际偏移。同一份混合 unit 导出可分别核查三个 core，但不能将整 unit 计数解释为三份独立来源证据。

对每个实际协议至少核查健康新连接、受控认证失败（协议有明确日志时）、普通网络错误，并将实际发生条件与投影结果对照。单次请求只验证格式/分类，不验证攻击阈值。没有明确失败日志的协议保持未验证；Hysteria2 目前仅连接观察，Xray Trojan 两类拒绝记录仅 fallback 候选。健康 fallback 应作为普通流量对照。

报告中的 `unverified` 不会因完成一次本机检查自动变为可信。需要为每条路径保留上述来源对照；已列出的中转地址会排除失败导出，未列出的中转不能自动识别。

## 仅观察接入的前置条件

当前规则仍为离线样板，项目没有生产安装入口。真实样本与来源对照通过后，再按该部署版本制定生产观察接入方案：

- 只采集有明确来源/时间依据的已适配事件，投影文件仅允许可信服务写入；防止伪造事件诱导告警或决策。
- 同一事件只采集一次，核查现有文件通配符、整 unit journal 和多个 core 重复匹配；确定偏移、轮转重开和重启后的行为。
- 使用专用标签，原始 V2bX 日志不能直接作为当前规范化 parser 输入；短样本 CLI 不能当长期 tail daemon 使用。
- 逐项核查实际 profiles：`remediation: false` 场景在忽略 Remediation 的自定义 profile 下仍可能产生决策；须在隔离副本验证后才能接入。
- 记录正常负载下日志容量、解析/忽略率、告警频率、CPU/内存及磁盘增长，再决定观察窗口和容量；不默认启用全量 debug/access。
- 明确停用观察采集/规则与恢复旧配置的方法；既有 SSH/Web 防护及其决策单独保留，不将全局 decisions 为空作为生产验收标准。

仅观察验收应确认：受控目标事件形成预期告警，健康连接/fallback、普通错误和共享中转不形成失败告警；本次场景未新增任何决策。原有其他场景可能已有正常决策，应按场景及时间核查增量。

## 封禁与限速的后续条件

只有已确认用户归因、误报和执行位置的路径才能进入封禁测试。使用独立测试来源与正常客户端对照，核验新增短时决策、Bouncer 同步、实际新连接阻断、正常中转可用及撤销后恢复，并记录既有连接是否受影响。不要对共享中转或管理出口作业务测试封禁。

共享中心决策可能在所有订阅 Bouncer 上生效，需要先核查范围；远端 Bouncer 本身不检测协议行为，也不从落地日志恢复用户地址。复用中心/远端方案时参见 [运维边界](remote-bouncer-operations.md)。

连接限速需入口正常峰值、机器容量及中转汇聚预算；用户限速/设备限制按实际 core 与面板验证。带宽攻击超过链路容量时仍需上游防护。以上步骤未实际执行前，阶段路线的生产验收项保持未完成。

## 隔离模拟方式

没有真实 VPS 时，可用独立 QEMU 客机和内部网络命名空间先验证来源可见性、LAPI/Bouncer 同步、健康客户端对照与封禁恢复。宿主不支持网络命名空间时，不取消隔离保护，应在客机内部运行；不共享生产目录或外网接口。具体网络层实验及失败轮次见 [模拟验收记录](audit/2026-10-13-v2bx-vps-simulation.md)。

回显 TCP/UDP 服务的网络测试不能当作 V2bX 三内核协议验收。要验证协议检测，还需在客机内运行固定版本的 V2bX、受控面板配置和真实协议客户端，记录实际产生的事件与包源。模拟的延迟/吞吐也不能用于设置真实 VPS 的限速阈值。

补充的 [真实协议隔离验收](audit/2026-10-13-v2bx-real-protocol-simulation.md) 运行了官方 V2bX 三内核与真实协议客户端，并回放实际日志投影。它验证指定版本、基础传输和受控账号；未完成的日志格式、IPv6 真实协议、其他传输和目标生产路径仍需逐项验收，不能沿用网络回显通过结论。

## 持久观察采样的部署前检查

可先用 `--v2bx-observe` 在当前用户的私有目录保存固定投影；同一源只运行一个采样器，禁止把重叠导出快照重复接入 acquisition。核查 `ignored` 分类和 `rotations/truncations/continuity_risks`，不能把部分未知格式或风险计数解释为攻击。该入口没有创建生产观察服务。

轮转前确认 V2bX 是否重开日志，若必须重启，应在维护窗口独立验收；采样器读到旧fd的EOF不代表写入者已经换fd，晚写可能漏采。copytruncate可能毁掉未读字节，锚点也不能识别所有相同前缀快速重写。当前隔离对照先停止／排空旧程序再启动新日志，不能泛化成任意生产轮转无损。

真实VPS仅观察仍需要指定版本、实际日志位置、文件属主与服务启动方式、每条入口的中转来源范围、现有acquisition和profiles。取得这些证据后，再在同版本隔离副本确定采集重开、去重、容量、告警和停用方式；没有这些部署证据不能将模拟结果标为生产观察完成。当前结果见 [日志与稳定性验收](audit/2026-10-13-v2bx-observation-stability.md)。

hysteria2 core新增事件目前来自 [实验fork补丁](../experimental/v2bx-hy2/README.md)，仅固定v0.4.0来源与依赖经过隔离验收。生产必须先判断是否运行官方包或该明确标识的实验构建；不要把官方日志缺失归为攻击消失，也不要自动替换二进制。sing Hysteria2不共享此认证实现；中转peer继续排除。

sing三个QUIC协议的观察事件也来自 [配套实验源码补丁](../experimental/v2bx-sing-quic/README.md)，需要同时核实sing-box_mod安全logger、sing-quic认证分支和本地依赖替换，不能仅凭V2bX版本号推断覆盖。仅标准日志factory经过验收；新增记录使用固定v2bx-auth前缀，适配器拒绝初版敏感inbound标签格式。每Service限额、丢弃摘要和中转CIDR需按实际节点数量／入口核查。最新隔离结果见 [sing QUIC报告](audit/2026-10-13-v2bx-sing-quic-events.md)。

多账号、IPv6 和 UDP 应用的新增隔离证据见 [配置对照验收](audit/2026-10-13-v2bx-mixed-ingress.md)。固定 hysteria2 core 依赖中 `ListenIP=::` 会选择 udp6，不能推断同时接收 IPv4；应结合实际监听及真实地址族连接核验。Shadowsocks 原生 UDP 中转需要另外开放 UDP 监听，TCP 转发成功不足以验收 UDP。两个地址族都有模拟证据，生产路径仍需重做。
