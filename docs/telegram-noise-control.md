# Telegram 分级降噪通知

普通扫描每小时汇总，未知规则先提醒，持续防护组件故障紧急通知。全部 CrowdSec 告警和决策继续按原规则处理，分级只决定何时通知。

## 启用与恢复

先更新完整仓库，在 `sudo bash crowdbastion.sh --telegram` 的第 1 项配置通知目标，再进入 **6 → 1** 启用分级通知。也可以运行：

```bash
sudo bash crowdbastion.sh --telegram-smart
sudo bash crowdbastion.sh --telegram-smart-status
```

启用和更新前均校验通知目标、配置与 profiles 中的通知通道引用；无法确认原服务的运行或启用状态时停止修改。服务先通过本地就绪检查，再加载 CrowdSec 通知配置；失败恢复原配置和原通知服务状态，包括原有的临时启用（`enabled-runtime`）。就绪只表示本地接收和发送队列可用，不代表首次健康检查已完成或 Telegram 已送达。启用不会主动发送测试消息。菜单第 2 项或 `--telegram-test` 会发送真实测试消息，依次验证官方插件渲染、本地持久化队列和 Telegram API 回执。单纯入队不会报告送达成功。

通过 **6 → 3** 或 `--telegram-smart-disable` 恢复启用前的即时/批量通知模式。菜单第 4 项停用整个本工具 TG 通道时，也会停用分级服务。两种停用均保留队列，重新启用后会继续处理待发消息。修改 Token/Chat ID 前先恢复原模式，再通过第 1 项修改目标。

交互机器人在菜单第 5 项更新安装后，同一 Token/Chat ID 的紧急卡片支持“已知晓”和“查看详情”。只有已配置的管理员在指定聊天中可以操作。未安装交互机器人时不显示按钮，也可以在本机确认：

```bash
sudo python3 lib/crowdsec_notify_setup.py ack /etc/crowdsec --id 卡片中的事件编号
```

“已知晓”仅停止该事件后续紧急催办，恢复和新一轮故障继续通知，不会解封、加白或更改防护。普通查询菜单仍然可用。

## 默认策略

| 类别 | 条件 | 通知 |
| --- | --- | --- |
| 普通 | 明确列入 `routine_scenarios` 的扫描、SSH 失败和 V2bX 观察规则；模拟告警 | 每 3600 秒一条静默汇总，无事件不发送 |
| 关注 | 未分类的新规则；检查状态持续未知；普通规则接收量在 300 秒内达到 100 条，且涉及至少 3 个不同分钟桶 | 首次提醒；同类新增事件 1800 秒内合并；不同关注事件最多每 60 秒合并发送一次 |
| 紧急 | CrowdSec/LAPI/已配置防火墙 Bouncer 连续异常至少 60 秒；显式配置的可信紧急规则 | 立即排入优先队列，绕过普通汇总和关注冷却 |
| 恢复 | 已产生事件的组件连续正常至少 120 秒 | 发送一次恢复通知 |

健康检查每轮完成后间隔 20 秒，故障/恢复时限还包括采样和检查耗时。检查间断超过允许窗口会重新累计连续时长；未知状态不算恢复。防火墙 Bouncer 未配置且节点用途不要求该组件时，不按故障报警。

组件退出监测范围时，结束已有事件及催办，并发送一次“停止监测”，不宣称故障恢复。若重新纳入监测，会撤销尚未发送的“停止监测”消息；同组件再次确认异常时，也会撤销旧的待发恢复消息，避免过时通知造成误解。

未确认的紧急事件在首次成功投递约 5、15、30 分钟后提醒，之后每小时提醒。检测类事件在没有新告警且已通知的情况下，空闲 30 分钟结束提醒；这不证明业务或安全事件已经恢复。健康故障必须取得连续正常检查结果才关闭。

同一节点按服务映射和规则聚合，不因攻击 IP 更换而新发一张卡片。默认没有服务映射时按规则聚合，可在配置顶层 `scenario_services` 填写精确规则名到服务名的映射。汇总展示最多 6 类事件及其余类别数量；来源数是当前事件在留存期内的独立来源数，不是新增消息窗口的精确来源数。完整告警通过 `/inspect` 或 `cscli alerts` 查询。

## 配置与运行

私有配置：`/etc/crowdsec/crowdbastion-notify.json`，权限 `600`。可调整 `policy` 中的窗口、计数及精确规则名列表；修改后重新运行 `--telegram-smart` 校验并加载。`critical_scenarios` 默认为空，只应填写具有可靠紧急含义的可信规则名。模拟告警始终汇总，攻击者控制的请求路径、UA 和 Meta 不能自行提升等级。

主通知配置必须是有效的 JSON 对象；配置读取只接受不超过 64 KiB 的普通文件。可选的交互机器人配置损坏或不可读时，紧急通知仍会发送，仅省略操作按钮。

不要将“存在封禁决策”当作已经成功拦截，也不要将漏洞攻击尝试当作已经入侵。默认规则列表之外的事件属于关注级，不会静默丢弃。告警速率阈值只是初始值，建议结合实际接收量调整。

- 服务：`crowdbastion-notify.service`，独立于 CrowdSec 运行，CrowdSec 停止不会连带停止通知检查。
- 程序：`/usr/local/lib/crowdbastion-notify/`。
- 状态：`/var/lib/crowdbastion-notify/queue-<目标指纹>.sqlite3`，SQLite WAL/FULL 提交；父目录 `700`。不同 Bot Token/Chat ID 使用独立队列，修改目标不会将旧消息发往新聊天。
- 入口：默认 `127.0.0.1:7423`，私有 Bearer 密钥验证；最多同时处理 16 个请求，满载返回可重试的 HTTP 503。官方插件只投递告警 ID、规则、模拟标志、来源和时间，不转发完整请求日志。
- 路由：继续使用 `crowdsec_1key_telegram`，仅修改通知目的地，不更改 profiles 的过滤、顺序或封禁决策。只有匹配现有通知路由的告警进入降噪服务。

去重记录默认保留 7 天，冷却、确认、重试及待发消息均持久化。网络错误按消息退避重试；Telegram 429 的 `retry_after` 对全部自动通知生效，由队列持久化，重启后也保留，不依赖可选诊断文件写入成功。紧急消息优先于到期的普通消息，但仍须等待正在进行的单次请求及 API 限流。网络超时或“API 已接受、进程尚未提交成功状态”之间崩溃可能造成重复投递，不能保证严格只发送一次。

`--telegram-smart-status` 显示队列数量、失败待重试数量、未恢复紧急事件、最近投递/失败时间以及检查心跳年龄。返回码 `0` 表示心跳正常且没有失败待重试消息；`2` 表示未启用或首次健康检查尚未完成；`1` 表示心跳过期、仍有失败待重试消息或操作失败。另一条消息发送成功不会掩盖仍未送达的失败消息。状态正常不代表所有防护组件正常，组件故障仍以事件和健康详情为准。

通知接收或健康检查线程停止、健康检查长期未更新时，通知进程退出，由 systemd 重启；日志使用 `journalctl -u crowdbastion-notify.service`。通知服务或磁盘故障期间，官方插件的重试有限，本地服务未成功接收的事件可能需要从 CrowdSec 记录中核对补查。

默认监测范围是本机 CrowdSec 服务、LAPI 可用性和已配置的防火墙 Bouncer 进程状态，不能证明每个网站实际拦截有效，也未包含业务 URL 探测、主机入侵检测或外部探测。整机断网/离线仍需外部监控与独立通知渠道。紧急消息使用正常 Telegram 通知，但无法绕过用户对聊天或手机设置的静音。
